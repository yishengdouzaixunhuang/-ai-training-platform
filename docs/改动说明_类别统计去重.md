# 改动说明：消除类别统计的重复计算（A 项）

**日期** 2026-11-06 · **文件** `ui/class_table.py`、`ui/main_window.py`、`ui/class_dialog.py`
**改动量** +20 / −8

---

## 一、问题

切换一个工程，`_compute_counts()` 被调用 **2~3 次**。实测（打开两个工程）：

| 工程 | 调用次数 | 各次耗时 |
|---|---|---|
| 眉山中航 2001 张 | 2 次 | 506 + 268 = 774 ms |
| 速博达（分类工程） | 3 次 | 158 + 102 + 87 = 347 ms |

两次之间相隔 527ms / 194ms，远超一帧，所以**不是同一帧里的重复触发**，
而是三条独立的刷新路径各自算了一遍。防抖解决不了。

## 二、三个触发点

`_compute_counts` 全项目只有两个调用点：`set_classes()`（L277）和 `refresh_counts()`（L315）。
但上游有三条路会走到它们：

| # | 路径 | 说明 |
|---|---|---|
| A | `set_project_dir()` → `set_classes(self._classes)` | **算的是旧类别**，且所有调用方紧接着都会用真正的类别再调一次 `set_classes` |
| B | `_refresh_class_ui()` → `singleShot` → `_deferred_class_counts` → `refresh_counts()` | 正常路径，该算 |
| C | `_load_classification_labels()` → `set_classes(labels)` | 分类工程专有，类别确实变了，该算 |

2026-10-29 那次优化只改了 `_refresh_class_ui` 里那一行（加 `with_counts=False`），
**漏了 A**——`set_project_dir` 内部还是 `with_counts=True`。

## 三、改了什么

**1. `set_project_dir(path, with_counts=True)` 加参数**

```python
if changed and self._classes:
    self.set_classes(self._classes, with_counts=with_counts)
```

默认 `True` 保留兼容语义；三个调用点显式传 `False`（它们自己都会用真类别再算一次）：

- `main_window._load_classification_labels` — 紧接着 `set_classes(labels)`
- `main_window._refresh_class_ui` — 紧接着 `set_classes(classes, with_counts=False)`
- `class_dialog._load` — 紧接着 `set_classes(list(self._classes))`

**2. 去掉 `_populate_image_list()` 末尾的 `_refresh_class_ui()`**

这条是 B 被触发两次的第二个来源。`_populate_image_list` 是后台扫描完成后的槽
（`image_list_signal.connect`），比 `_load_classes` 晚几百毫秒到几秒。

判断依据：`_compute_counts` 只依赖文件系统（`images/` 与 `annotations/` 的内容），
**跟列表行数没有关系**。列表建好后重算类别统计没有依据。

代码里留了注释，写明「若将来发现列表变了类别表却不更新，先回看这里」。

| 速博达 | 3 次（158+102+87） | **1 次（86）** |

## 五、请重点核对

1. ~~`_populate_image_list` 里那次刷新真的可以去掉吗~~ —— **审核发现确实漏了副作用，
   已修，见第八节**。原判断「统计只依赖文件系统」对分割工程成立，但 `_refresh_class_ui`
   尾部还负责同步推理参数面板和类别数标签，分类工程那条路径不经过它。
2. **`with_counts` 默认值给 `True` 是否合适** —— 目的是保留「单独调 `set_project_dir` 就有数字」
   的兼容语义。如果认为三条路径已覆盖全部场景，改成默认 `False` 更彻底，但风险更高。
3. **分类工程（速博达）从 3 次降到 1 次** —— 确认 C 路径（`_load_classification_labels`）
   的 `set_classes(labels)` 确实还在算，没有被我误伤。

## 六、没做的部分

审核建议用「合并请求（dirty 标志 + 一次调度）」而不是缓存，这个方向对，
但实测三条路径相隔 190~530ms，超出任何合理防抖窗口（计算本身就要 500ms，阻塞期间也收不到新请求），
所以最终没有走调度合并，而是**去掉了不该算的那一次**。

结果缓存（B 项）留到下一轮，它要处理失效判断，正好是这次踩过坑的地方，单独做。

## 八、审核另一轮：分类工程的副作用（2026-11-06 第四轮）

审核指出我上面第 1 条「选中行由 `_render_page` 兜住」的说法站不住，同时发现删掉那次刷新
在分类工程上留下了副作用。两条都核实成立。

### 1. 分类工程的推理面板会停在空类别（已修）

`_refresh_class_ui` 尾部有两件事只有它会做：

```python
self._update_class_count_label(len(classes or []))
if hasattr(self, "infer_params"):
    self.infer_params.set_project(self._project_dir_or_none(), classes)
```

而分类工程走的是另一条路 —— `_load_classes` → `_set_task("classification")` →
`_load_classification_labels`，后者只 `set_classes(labels)`，**不经过** `_refresh_class_ui`。
原来靠 `_populate_image_list` 那次刷新兜住（那时 `_cached_classes` 已是 labels），
我删掉后就没人补了。

**实测复现**（柳州国轩：`project.json` 的 `classes` 是 `[]`，真类别在 `class_labels.json`）：

| 版本 | 类别表 | 推理面板下拉 |
|---|---|---|
| A 之前 | NG, OK（2 行） | **NG, OK（2 项，启用）** |
| A 之后 | NG, OK（2 行） | **0 项，禁用** |

类别表有内容、推理面板是空的，用户看得见但不知道找谁。

**修法**：在 `_load_classification_labels` 里显式同步，手上就有 `labels`，不必猜
`_cached_classes` 是否已更新：

```python
self._update_class_count_label(len(labels))
try:
    if hasattr(self, "infer_params"):
        self.infer_params.set_project(project_dir, labels)
except Exception:
    pass
```

修复后复测：下拉恢复 2 项、启用。分割工程不受影响（眉山仍 1 次调用、数字 162/21/28 未变），
8 个回归脚本全绿。

### 2. 「选中行由 `_render_page` 兜住」这个因果是错的

`_render_page` 尾部恢复的是**图片列表**的选中行（按 `canvas.current_image_path` 匹配），
它完全不碰 `class_list` 和 `current_class_id`。

真实原因是：两次刷新之间 `canvas.current_class_id` 没有变化
（`_load_image_by_index`、`_render_page` 都不改它），所以第二次 `setCurrentRow` 与第一次
结果相同 —— **是幂等，不是兜底**。

差别在于幂等只是「当前恰好如此」。哪天 `_load_image_by_index` 开始按图的标注自动切当前类别，
这个前提就没了，选中行会停在旧值而没有任何东西接住。这条已按审核建议改掉，
不留错误的因果给后面的人。

### 3. B 项要记的一条

审核提醒：缓存键如果只挂 `_dir_index` 的签名，会漏掉 `class_labels.json` ——
它既不在 `images/` 也不在 `annotations/` 下，而分类工程的类别真源就在那里。
判失效时漏了它，改完类别数字不更新，比这次的 bug 更隐蔽。B 做的时候必须带上。
