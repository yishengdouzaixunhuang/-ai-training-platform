## 0. 一句话结论

这个项目的**代码质量不低**（`task_queue.py` 的设计注释、`OcrOcvMixin` 的拆分理由都写得很专业），真正的问题不是"写得烂"，而是**规模涨上来之后缺三样基础设施**：

| 缺什么 | 现在的表现 | 电商系统怎么解的 | 本清单怎么解 |
|---|---|---|---|
| **统一的失败语义** | 256 处 `except Exception:`，其中 **143 处紧跟 `pass`** | `BaseResult` + `CodeEnum` + `BusException` + `@RestControllerAdvice` | `core/result.py`：`Result` + `ErrCode` + 装饰器兜底 |
| **统一的配置入口** | **20 种 json** 散在根目录和工程里，7 组 save/load 方法埋在 `main_window` | Nacos 配置中心，代码零明文 | `core/settings.py`：声明式 `SettingsStore` |
| **每个任务自己的状态** | `self.trainer` 单槽 + `self._stop_flag` 全局标志 ⇒ 交接文档第 20 条那个 bug 的**根因** | 订单状态机（1→2→…→6，每条订单各带一份） | `Task` 扩展 `stop_flag`/`epochs`，全局标志退场 |

**不做**：不引入微服务、Dubbo、Nacos、网关——你跑在产线工控机上，那套东西的运维成本会直接压垮现场。**只借思想，不搬形式。**

**关键判断：为什么用 Mixin 而不是拆成独立 Controller？**

`OcrOcvMixin` 的注释里已经回答过了，我完全同意并沿用：

> 用 Mixin 而不是独立 Controller，是为了让所有 `self.xxx` 引用继续成立，零改动搬运、行为不变（这是重构里风险最低的做法）。

284 个方法里到处是 `self.canvas` / `self.pm` / `self.current_project` 这类跨域引用。改成组合（composition）意味着要给每个 controller 注入十几个依赖，**必然引入回归**。Mixin 只把方法**物理搬家**，`self` 语义一字不变——这是唯一能保证"拆完 9586 行行为完全一致"的路径。

## 4. P0 阶段：地基（零侵入，建议先做）

### ☐ P0-1  `core/result.py` —— 统一返回与错误码

**借自**：`BaseResult` + `CodeEnum` + `BusException`

现在的问题：`except Exception: pass` 143 处，出错就没了。用户看到"点了没反应"，开发只能翻 `crash_log.txt`。

**新建文件**（不碰任何现有代码）：

```python
# core/result.py
SUCCESS = 200
SYSTEM_ERROR = 500

PROJECT_ERROR   = 1000   # 工程 1000-1099
DATASET_ERROR   = 1100   # 数据集/划分 1100-1199
TRAIN_ERROR     = 1200   # 训练 1200-1299
INFER_ERROR     = 1300   # 推理 1300-1399
ANNOTATION_ERROR= 1400   # 标注 1400-1499
IO_ERROR        = 1500   # 文件/磁盘 1500-1599
```

```python
@dataclass
class Result:
    code: int
    message: str
    data: Any = None
    detail: str = ""          # traceback，只进日志不进界面

    @property
    def ok(self): return self.code == SUCCESS
```

配套三个小工具：

| 函数 | 作用 | 用在哪 |
|---|---|---|
| `ok(data)` | 构造成功 | 服务层返回 |
| `fail(code, msg)` | 构造失败 | 服务层返回 |
| `as_result(fn)` 装饰器 | 把异常转成 `Result`，**并记日志**，不再静默 | 逐步套到 `TaskQueue` 的任务函数上 |

**验证**：新增 `tests/test_result.py`，5 条断言（成功/业务失败/未捕获异常/嵌套调用/日志落盘）。不涉及 UI，`python -m pytest` 直接过。

**风险**：零。纯新增。

### ☑ P0-3  `task_queue` 增强 —— 任务级状态，根治全局标志

> **2026-11-11 已完成**，实现与验证见 `docs/改动说明_任务级停止标志.md`。
> 与下面原设计的两处差异：① `Task` 没有新增 `stop_flag` 字段，而是把它做成
> `cancel_requested` 的**读写别名**（两份状态迟早打架）；② `epochs_done/total`
> 没加，已有 `done/total` 就是同一个东西。另外实际读代码时发现两个原设计没提的病灶：
> **分类训练根本不走队列**（裸线程，与分割训练共用全局标志）、
> **提交那一刻就清全局标志**（把用户刚点的取消抹掉），都已修。

**借自**：订单状态机（每单带自己的状态、时间戳、超时）

这是**我认为最有价值的一项**，因为它解决的是交接文档第 20 条那个 bug 的根因。

现状病灶：

```python
self.trainer      = None     # 单槽位，任务 A 和任务 B 抢
self._stop_flag   = False    # 全局标志，任务 A 的取消会误伤任务 B
```

交接文档打的补丁是"局部快照 + 只清自己那个"——**治了症状，没治病**。

**改法**：给 `Task` 加三个字段（`ui/task_queue.py`，改动约 20 行）：

```python
@dataclass
class Task:
    ...
    stop_flag: bool = False          # 这个任务自己的停止标志
    epochs_done: int = 0             # 训练：已完成 epoch
    epochs_total: int = 0
    phase: str = ""                  # ""|"preparing"|"training"|"validating"|"saving"|"inferring"
```

`_Ctx` 增加两个方法（供任务函数调用）：

```python
def phase(self, name):  ...   # 上报当前阶段，UI 可以显示"正在验证…"
def stop_requested(self): return self._t.stop_flag
```

**调用点改造（唯一一处侵入）**：

| 位置 | 现在 | 改成 |
|---|---|---|
| `_start_training` L8260 | `self._stop_flag = False` + `stop_check=lambda: self._stop_flag` | `ctx.task.stop_flag`，每个任务一份 |
| `_stop_training` L8247 | 改 `self._stop_flag` | 改 `queue.request_cancel(当前任务id)` |
| `run()` 内的 `finally` | 复位 `self._stop_flag`（因为全局） | **不需要了**——任务结束时它自己的标志随对象消失 |
| `_cleanup_trainer` L8562 | `if self.trainer is target` 判身份 | **可以简化**——trainer 挂到 `ctx.task` 上，天然隔离 |

**收益**：`self._stop_flag` 这个类属性可以彻底删掉，第 20 条那个 bug 的**根因消失**，不再是"小心点别踩"。

**验证**：`selftest_taskqueue.py` 现有 21 条断言必须先全绿；再补 6 条（两任务并发时 stop_flag 互不影响、phase 上报、取消后对象状态）。

#### ⚠️ 附：`closeEvent` 重复定义是一个**正在发生**的 bug

这不是"死代码清理"，是**功能丢失**。Python 类里同名方法后定义者胜，所以：

| | L234 的版本（**从未执行**） | L6899 的版本（实际生效） |
|---|---|---|
| 停系统监控 `_sys_monitor.stop()` | ✅ | ❌ |
| 保存分类训练参数 `_save_cls_train_settings()` | ✅ | ❌ |
| 注销全局热键 `unregister_global_hotkey(...)` | ✅ | ❌ |
| 保存分割训练参数 `_save_panel_train_settings()` | ❌ | ✅ |
| `super().closeEvent(event)` | ✅ | ✅ |

**后果**（都能在代码里对上）：
1. `_sys_monitor` 的采样线程从未被停止 → 关窗后后台线程残留
2. `_screen_ocr` 注册的**全局热键从未注销** → 平台关掉后热键仍被占用，下次启动注册可能失败
3. 分类训练参数在关窗时**从来没存过** → 用户改了分类参数、关掉、再打开就回滚（交接文档提到"避免重启后回滚"，那个意图正是被这行覆盖掉的）

**修法**（合并成一个）：

```python
def closeEvent(self, event):
    """关窗前：停监控、存两套训练参数、注销热键。"""
    if hasattr(self, "_sys_monitor"):
        self._sys_monitor.stop()
    for fn in (self._save_panel_train_settings, self._save_cls_train_settings):
        try:
            if getattr(self, "_project_dir", None) or fn is self._save_panel_train_settings:
                fn()
        except Exception:
            pass
    if getattr(self, "_screen_ocr_global", False):
        try:
            unregister_global_hotkey(int(self.winId()), self._screen_ocr_hotkey_id)
        except Exception:
            pass
    super().closeEvent(event)
```

## 5. P1 阶段：拆 God Object（Mixin 搬运，零行为变更）

**统一操作手法**（每一步都一样，不存在"这一步特殊"）：

1. 新建 `ui/mixins/<name>.py`，类声明 `class XxxMixin:`，把方法**原样剪切**过去（连注释、连缩进）
2. `main_window.py` 顶部 `from ui.mixins.xxx import XxxMixin`
3. 类声明从 `class MainWindow(OcrOcvMixin, QMainWindow)` 改成 `class MainWindow(XxxMixin, OcrOcvMixin, QMainWindow)`
4. **确认 MRO 顺序**：Mixin 必须在 `QMainWindow` 之前，否则同名方法（如 `resizeEvent`、`eventFilter`）被子类覆盖
5. 跑验收门禁（见 §7）
6. `git commit` 一个独立提交，出问题整块 revert

**每一步都必须遵守**：一次只搬一个 Mixin，绝不"顺手改了别处"。
