# 改动说明：切换工程时画布/列表同步清空（用户报「右边没跟着换图」）

**日期** 2026-11-11 · **文件** `ui/main_window.py`、`tests/test_project_switch_view.py`（新增 5 条）
**起因** 用户实拍：在「工程管理」里双击切换工程，右边画布还是上一个工程的图。

---

## 一、实测：不是"没切换"，是"切换期间还挂着上一个工程"

用真实工程量（`_probe_switch_canvas.py`，只读）：

| 工程 | 列表就绪 | 首图出现 |
|---|---|---|
| 海目星二期（2001 张） | **9577 ms** | **10814 ms** |
| 速博达（538 张） | 893 ms | 1213 ms |

两件事叠在一起：

1. `canvas.set_project()` 只设 `project_dir` / `label_manager`，
   **不动 `image` / `mask` / `current_image_path` / 叠加层**；
2. 新工程的首图要等 `_load_image_list_async` 扫完、`_render_page` 收尾才加载。

⇒ 双击后的 **10 秒里，画布一直显示上一个工程的图**（连文件标签、已标注数都是旧的）。
用户看到的就是"没切换"。

### 顺带发现的真实风险（比看得见的那个更严重）

切换时 `label_manager` 已经换成**新工程**，而 `current_image_path` 还是**旧工程**的图。
`_mask_png_timer`（标注改动 → 写 `annotations/<base>_mask.png`，500ms 防抖）
如果在这期间触发，读的是当时的 `self._project_dir`（已变成新工程）+ 旧图的 `base`
⇒ **把旧图的掩膜写进新工程的 annotations 目录**。这个错很难被发现：
文件名对不上任何一张图，统计时被当成"多余的孤儿文件"。

## 二、改法

### 1. `_reset_view_for_project_switch()` —— 切换瞬间清干净

在 `_open_project_by_name()` 里**换 `_project_dir` 之前**调用（顺序很关键：
防抖定时器一触发就会读当时的 `_project_dir`）：

- **停** `_mask_png_timer`（上面那条风险）；
- 清画布：`image` / `mask` / `display_pixmap` / `prediction_overlay` /
  `current_image_path` / `_prediction_mask` / `_pred_prob` / 各级缓存
  （`_cached_qimage` / `_cached_gray` / `_cached_overlay_rgba_qimage` /
  `_heatmap_qimage` / `_ocr_overlay` / `_gray_image` / `_height_image`）；
- 清列表：`_all_images` / `_filtered_data` / `image_list_widget.setRowCount(0)` /
  `_pending_select_first=False`（不清行的话，双击旧行能把旧图又拉回来）；
- 信息栏归零（`文件 --`、宽高/已标注/耗时 `--`）、`Total: 0 images`。

`_close_project()` 也改用同一套（原来只清了画布的一半字段）。

### 2. `_preview_first_image()` —— 不等列表，先把首图显示出来

清空只解决"看到旧图"，接着用户会盯着**空白**等 10 秒。实测那 10 秒大头在
**列表构建**（扫描 + 掩膜统计预热），跟"显示一张图"没关系。

所以 `scandir` 拿 `images/` 里第一个图片名（2001 条约 10ms）+ 解码一张，
**约 0.3s 出图**。列表到位后 `_render_page` 会按 `current_image_path` 匹配到第 0 行
再加载一次（同一张图），顺带把选中行点亮 —— 预览和正式加载是同一份状态，不会打架。

⚠️ 只在 `images/` **顶层**找：分类工程的 `images/<类别>/` 布局直接跳过。
   猜错会显示别的类的图，比空白更让人困惑。

## 三、验证

`tests/test_project_switch_view.py`，5 条：

| 用例 | 钉住什么 |
|---|---|
| ★ 切换瞬间清掉旧工程的一切 | 返回时画布不许还是旧图；列表 0 行；`_all_images` 空；掩膜防抖已停 |
| ★ 不等列表就显示新工程首图 | 返回时画布已经是**新工程**的图（钉预览） |
| 最终加载新工程首图 | 清理不能把正常流程弄坏 |
| 关工程也清空 | 同一个清理函数，别只修一半 |
| 来回切换不串工程 | A→B→A，每次都不许停在上一个工程的图上 |

变异检验（临时副本，改完还原）：

| 去掉什么 | 目标用例 | 结果 |
|---|---|---|
| `_reset_view_for_project_switch()` 调用 | 切换瞬间清掉旧工程的一切 | **红** |
| 只去掉 `_mask_png_timer.stop()` | 同上 | **红** |
| `_preview_first_image()` 调用 | 不等列表就显示新工程首图 | **红** |

**3/3**。全套 **13 个脚本 96 项**全绿；`.task_history.json` 前后 md5 一致。

### 真实工程上的效果

| 工程 | 改前"看到新工程的图" | 改后 |
|---|---|---|
| 海目星二期（2001 张） | 10.8 s（这 10.8s 里显示的是**上一个工程**的图） | **1.1 s**（其间不再显示旧图） |
| 速博达（538 张） | 1.2 s | **0.4 s** |

## 四、请重点核对

1. **调用顺序**：`_reset_view_for_project_switch()` 必须在 `self._project_dir = 新工程`
   之前。挪到后面就会重新引入"防抖把旧图写进新工程"的窗口。
2. **预览的取舍**：预览只认 `images/` 顶层第一个文件（按文件名排序），
   分类工程（`images/<类别>/`）不预览、仍然是空白等列表 —— 这是刻意的。
3. **多一次解码**：预览一张 + 列表到位后再加载同一张，等于同一张解码两次
   （4096² 约 0.3s）。换"立刻能看到图"这笔账算得过；如果以后嫌慢，可以让
   `_load_image_by_index` 发现"路径没变就直接复用"，不要在预览里做特殊判断。

## 五、没做的部分

- **列表构建那 9.6 秒本身没优化**。它是"扫描 2001 个文件 + 掩膜统计预热"的真实开销，
  属于另一件事（可考虑先出列表、统计后补，像类别统计那样）。本次只保证
  "切换后立刻看到新工程的东西 + 不串工程"。
- 预览不处理多视图分组（先显示组里排序第一张，正式加载会按组纠正）。

## 六、审核第二轮（2026-11-11）：三点建议全采纳

### 1. 字段清单搬进 canvas（原来硬编码在主窗口）

审核说得对：15 个 `setattr(c, attr, None)` 写在 `MainWindow` 里，**谁给 canvas 加一个
`_cached_xxx`，这里必然漏**，而漏了的症状和这次一模一样（看到上一张的残影），
下一轮排查要从头再来。

现在清单在 `AnnotationCanvas.reset_view()`（`annotation/mask_editor.py`），
**加字段的人和清字段的人在同一个文件**。清的范围也扩大了（原来主窗口那份漏了）：

| 组 | 字段 |
|---|---|
| 图像/掩膜 | `image` `mask` `display_pixmap` `current_image_path` `_cached_qimage` `_cached_gray` |
| 叠加层 | `prediction_overlay` `_prediction_mask` `_pred_prob` `_cached_overlay_qimage` `_cached_overlay_rgba_qimage` `_det_overlay` `_heatmap_qimage` `_show_heatmap` `_ocr_overlay` `_overlay_dirty` |
| 每图统计缓存 | `_pred_overlay_cache` `_pred_stats_cache`（**原来漏了**，会拿上一张的统计画这一张） |
| 高度图 | `_height_image` `_cached_height_qimage` `_cached_height_pil` `_height_path` `_height_vmin` `_height_vmax` `_gray_image` |
| 交互中间态 | `_cursor_pt` `_drawing` `_polygon_points` `_stroke_pts` `_drag_start_pos`（半截多边形不能跨工程留着） |
| 视图几何 | `zoom_level` `pan_offset_x/y` |

刻意**不清**的：`_mode` / `current_class_id` / `brush_size` / 各种显示开关 /
`_height_colormap` —— 那是用户偏好，不是这张图的状态。

另加一条护栏用例：`_reset_view_for_project_switch()` 的源码里**不许再出现**
`_cached_qimage` / `_prediction_mask` / `_pred_prob` / `_cached_gray` 这些字段名
（谁把它们搬回主窗口，测试当场红）。

### 2. 预览排序必须和列表一致

审核问得对，我查了：`_load_image_list_async` 里是 `sorted(os.listdir())` ⇒
**默认顺序就是字典序**，预览用 `min(名字)` 一致，没问题。

但有个例外：勾了「Recent」时列表按**标注 JSON 的 mtime 降序**（`_filter_rows_body_impl`
里的 `images.sort(key=_json_mtime, reverse=True)`，稳定排序）。这种情况下预览还是字典序
就会"预览一张、列表选中另一张"。现在预览跟随同一个规则：

```python
if self.recent_check.isChecked():
    first = sorted(imgs, key=lambda n: (-json_mt.get(stem, 0.0), n))[0]   # mtime 降序 + 同名次取小
else:
    first = min(imgs)
```

JSON 的 mtime 顺手在同一次 `scandir` 里拿到（Windows 上 `DirEntry.stat()` 不额外发系统调用）。

### 3. "有图无列表"的 9.6 秒中间态：钉住了

审核建议自查两件事，现在做成用例 `test_autosave_during_preview_window_goes_to_new_project`：
驱动"清理 → 换目录 → 预览 → 画一笔触发 `_sync_mask_png_for_current()`"，断言

- 掩膜写进**新**工程、文件名对应**预览那张图**；
- **旧**工程的 `annotations/` 一个文件都没多。

导航键那条审核已经自己验过（`_next_image`/`_prev_image` 用 `currentRow()`，清空后是 -1，不越界）。

### 4. 变异检验（临时副本，改完还原）

| 去掉什么 | 目标用例 | 结果 |
|---|---|---|
| 预览忽略「Recent」排序（改成永远 `min`） | 预览排序跟随「Recent」 | **红** |
| 主窗口又把 `_cached_qimage` 写回去 | 清字段清单住在 canvas 里 | **红** |
| 预览不加载图片 | 中间态自动保存写进新工程 | **红** |

**3/3**。全套 **13 个脚本 100 项**全绿。

### 5. 顺手：`torch` 必须先于 `PyQt5` 又踩了一次

给测试加模块级 `from PyQt5.QtCore import Qt` 时忘了这条规矩，整份用例炸在

## 七、审核第三轮（2026-11-11）：这轮被**驳回** —— 我搬进去的清单一行都没执行

审核实锤：`annotation/mask_editor.py` 里有**两个** `reset_view`：

```
145 行   def reset_view(self):   ← 我这轮新加的，58 行，清 20 多个字段
2420 行  def reset_view(self):   ← 既有的，工具栏「刷新视图」用，4 行 _fit_to_window()
```

两者都在 `AnnotationCanvas` 里。**Python 类体里后定义的覆盖先定义的** ⇒ 生效的是 2420 行那个
4 行版本，我搬进去的清单**一行都没跑**；而主窗口那 15 个 `setattr` 已经删掉了。

净效果：**切换工程时一个字段都没清**（改之前的 `74a706a` 至少清 15 个）。
用户会看到「新工程的图上叠着上一个工程的预测掩膜/热力图」，比"看到旧图"更隐蔽 ——
图是对的，上面却多了莫名其妙的预测块。而这正是本轮专门补的三处漏项要解决的问题。

### 1. 为什么 10 条测试全绿

`test_switch_clears_view_immediately` 只断言 `current_image_path != 旧图`。而
`_open_project_by_name()` 在清理**之后**紧接着调 `_preview_first_image()`，
`canvas.load_image()` 顺手把这个字段覆盖成新图了。

**唯一被断言的字段，恰好被预览救了。** 其余缓存字段无人过问。

### 2. 为什么变异没抓到（这条比 bug 更值得记）

上一轮的变异是「主窗口又写回 `_cached_qimage` → 源码扫描红」。那条打在**源码文本层**，
绕过了执行路径。如果把变异改成「删掉清理逻辑」，测试**根本不会红** —— 因为那段代码本来就没跑。
**变异护住了一个不存在的东西。**

⇒ 教训：**变异必须打在会被执行的那条路径上**。源码文本断言（"函数里出现了 reset_view()"）
证明不了"它真的被调用"。

### 3. 修法

`reset_view` 那个名字属于工具栏「刷新视图」（`ui/main_window.py:6919` 在用，**不能删**），
所以给新方法改名：

```python
# annotation/mask_editor.py:145
def reset_for_project_switch(self):   # 原 reset_view
    ...

# ui/main_window.py:3565
self.canvas.reset_for_project_switch()
```

实测两者各就各位：`reset_view` = 4 行（窗口适配），`reset_for_project_switch` = 63 行（清理）。

### 4. 新增两条护栏

**① `tests/test_duplicate_defs.py` —— 类内重名方法扫描（审核建议）**

用 `ast` 遍历每个 `ClassDef` 的直接子节点，按方法名分组，≥2 次即报。
排除语言允许的情形：`@property` + `@x.setter/getter/deleter`、`typing.overload`、
`singledispatch.register` —— 否则会把那 4 处正常的 property 对误报成 bug。

自带两条自检（喂一段"真有重名"、一段"property+overload"），
因为**没有自检的静态检查最危险：写错了就返回空列表，测试永远绿**。

扫 190 个 `.py`，当前 **0 处**真重名。

**② `test_reset_actually_clears_canvas_fields` —— 哨兵值用例**

往每个字段塞互不相同的哨兵值（字符串、dict、list、ndarray），直接调
`_reset_view_for_project_switch()`，逐个断言清干净；再验证用户偏好
（`brush_size` / `current_class_id`）**不被清**。

不像 `test_switch_clears_view_immediately` 那样经过预览，所以不会被"预览顺手覆盖"掩盖。

### 5. 变异检验（这次打在执行路径上）

| 塞回的形状 | 目标用例 | 结果 |
|---|---|---|
| 方法名改回 `reset_view`（复现事故） | 全项目无类内重名覆盖 | **红** → `annotation/mask_editor.py → class AnnotationCanvas → def reset_view [145, 2426]` |
| 同上，走执行路径 | ★ 清理真的执行（哨兵值） | **红** → 列出所有没清的字段 |

| 主窗口干脆不调清理 | ★ 清理真的执行（哨兵值） | **红** |

**4/4**，还原后逐字节一致。全套 **14 个脚本 104 项**全绿，`.task_history.json` md5 未变。

真实工程复测（只读探针）：看到新工程首图 **894 ms**（海目星二期 2001 张）/ **317 ms**（速博达）。

### 6. 两个顺带踩到的坑

- **CRLF**：`annotation/mask_editor.py` 整份是 CRLF，变异脚本里的锚点写 LF 就一条都匹配不上。
  读文件时先 `.replace("\r\n", "\n")` 归一化。**注意：改真实文件时不能顺手把换行符也改了**
  （本轮 `mask_editor.py` 的 diff 只有 +7/−1 行，确认没被整体重写）。
- **UTF-8 BOM**：`test_duplicate_defs.py` 第一版用 `io.open(encoding="utf-8")` 读源码，
  结果全项目一半文件报"语法错误"（BOM 变成 `U+FEFF`）。改成把 **bytes** 交给 `ast.parse`，
  让它自己按 coding cookie / BOM 解码。
