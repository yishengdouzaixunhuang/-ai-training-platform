先看结论：为什么必须看 10 项而不是 1 项

拿本项目真实数据跑一个"中等质量"的模型，同一份预测结果算出来的数字是这样的：

FWIoU 0.9997

Macro Recall（不漏） 0.9858
Boundary F1（轮廓） 0.5863

PA = 0.9998 看起来"几乎完美"，但同一份结果： 9 个真缺陷里漏了 6 个，还多报了 7 个假缺陷。 原因很简单——缺陷只占全图 0.0103% 的像素， 全判背景也有 0.9999 的 PA。

一、十项指标：分四层看

顺序是有讲究的：像素级 → 类别级 → 边界级 → 目标级。越往下越接近产线关心的事， 也越不容易被"类不平衡"骗到。宏平均一律只统计前景类（排除 background）。

从这张表读出的三条规律

  • PA / FWIoU 全程 ~0.9999，六种场景（含零检出）几乎不动 → 它们只能证明"模型没崩"，不能用来评价好坏。
  • Kappa / mIoU / Dice 同步动，适合做模型迭代的主指标： ① → ⑤ 是 1.00 → 0.63 / 0.46 / 0.63，单调、可比较。
  • 只有区域级能分辨"漏检 vs 过杀"： ② 膨胀造成的是"目标粘连"（3→2 个），④ 造成的是"1 漏 1 多"。 像素级看不出这个区别，产线却只关心这个区别。

注意 ②：膨胀 5px 把两个相距很近的缺陷粘成一个，区域 IoU 掉到 0.5 以下 → 区域指标全归零。这类"粘连"缺陷在产线上比"漏检"更常见。

三、本场景的 8 个坑（都是实测踩到的）

  1. 类极不平衡：凹点前景只占全图 0.0103% 的像素。 PA、FWIoU、Specificity 这一族指标会系统性虚高，只用它们等于没评估。
  2. ignore 区域必须排除：标注里的 __ignore__ 多边形在掩膜里是 255 （本样本有 43,380 个 ignore 像素）。不排除的话，这些区域的预测差异会直接算进 FP/FN。
  3. 宏平均必须排除背景：否则 background 的 IoU≈0.9998 会把 mIoU 拉到 0.64 这种"看着还行"的假象 （仅前景只有 0.289）。
  4. 空类不能当 0：某类在预测里完全没出现时，Dice/P/R 无定义、HD95 无定义。 → 工具已将其记为 n/a 并单独计数，绝不悄悄当 0 摊进平均。
  5. 碎块会绑架 Recall：本样本标注里有 30px 和 32px 的小碎片。 按客户"最小可识别面积 ≥2mm²"的口径，这类碎片可能根本不该算漏检， 否则模型 Recall 会被无关紧要的小点压死。 → 工具已提供 --min-area 开关（默认 0 = 不过滤，阈值待你拍板）。
  6. IoU 0.5 的匹配阈值会放大"粘连"：膨胀 5px 就足以让两个相邻缺陷粘成一个、 区域 IoU 跌到 0.5 以下。这个阈值本身也是判据的一部分，要和报告一起记录。
  7. 全局累计 vs 逐图平均：本工具用全局累计（把全数据集的 TP/FP/FN 加起来再算）， 避免"小图/空图"把平均值拉偏；HD95 这类几何量只能逐图算，则报均值 + 最差值。
  8. 测试数据的 GT/Pred 语义必须一致：我们自测第一版就把 GT 的 ignore 区填成 0/1 噪声 却让预测保持原样，凭空造出 2 万个"伪缺陷目标"，把 BF/HD95/区域指标全部打崩 —— 当时差点误判成工具 bug。负样本的构造方式本身就会污染指标。

四、从像素指标 → 产线 KPI

客户 KPI 是电池级的：过杀率 ≤5%（分母 = 总产能）、漏检率 ≤0.2%。 分割指标是像素/目标级的，两者不能直接划等号。换算关系：

层级口径与产线的关系
像素级PA / mIoU / Dice 只说明"模型学到了没有"，不能泄漏给客户当过杀/漏检承诺
目标级区域 Recall / Precision 缺陷目标级的漏检/过杀，是最接近产线的中间量
电池级一块电池 = 一图或一组三视图 电池级漏检率 = 存在漏检目标的电池数 ÷ 总电池数
电池级过杀率 = 被判 NG 而实际 OK 的电池数 ÷ 总电池数

关键提醒：分割做到区域 P/R 双 100%，产线仍可能过杀爆表 —— 因为最终 NG/OK 是由判定阈值（ui/threshold_panel.py / Predictor.classify_with_threshold）决定的，不是分割精度决定的。 评估分割模型用这 10 项；调过杀/漏检要去调判定阈值。

五、怎么用

# 模式 1：已有"预测掩膜目录"（零 torch 依赖，最快；导出 HTML 报表）
python tools/eval_seg_metrics.py --gt-dir GT --pred-dir PRED \
    --class-names background,Atd --html report.html --json result.json

# 模式 2：直接评 DL Studio 项目（加载 best_model.pth，走部署同款推理路径）
python tools/eval_seg_metrics.py --project <项目目录> --split val \
    --model-file best_model.pth --html report.html

# 只评前 10 张先看趋势
python tools/eval_seg_metrics.py --project <项目目录> --limit 10

# 客户"最小可识别面积"口径过滤碎块（阈值待定）
python tools/eval_seg_metrics.py --project <项目目录> --min-area 100
参数默认说明
--tol2.0 边界级容差（像素）。影响 BF；HD95 不受它影响。改了就不可与旧报告直接比
--region-iou0.5 连通域配对阈值。放宽到 0.3 会容忍更多形态差异
--min-area0 区域级最小面积（像素）。小于它的碎块不计漏检/过杀。默认不过滤
--splitval 项目模式的评估集（train / val / all）

输出三样：① 控制台分层报表；② --json 机器可读结果（含混淆矩阵、逐类、逐图）； ③ --html 带判定色和混淆矩阵热力图的可视化报表。 右侧指标卡片按红/黄/绿着色，判据见上表。

七、待你拍板的四件事

  1. --min-area 取多少？ 客户口径"最小可识别面积 2mm²"折成像素需要先确认标定 （按 0.14mm/px 约 102px，按 0.037mm/px 约 1460px，两者差 14 倍，必须先定标定）。 定下来之前默认不过滤。
  2. --tol（边界容差）默认 2px 是否合适？ 取决于缺陷边缘的判定精度要求。
  3. 各指标的合格线：报表里现在用的是工程经验值（PA≥0.99、mIoU≥0.85、区域 R≥0.99…）， 是否按客户 KPI 重新标定？
  4. 要不要接进 DL Studio 界面？ 目前训练只打印 mIoU + 逐类 IoU， 评估结果没有落到界面。可以加一个"评估"页签（10 项指标卡片 + 混淆矩阵 + 区域漏检/过杀）。
