结论一：差距不在「算子流框架」，那条路我们已经走完大半。
DL Studio 已有 flow/ 包（frame.py / node.py / registry.py / runner.py / batch.py） 与 ui/flow_editor.py 流程编辑器，节点已覆盖 cls/det/seg/ocr/ocv/visualize/calculator/output —— 与 iCogtiveFlow 的 「流程配置 → 拖工具节点 → 连线」是同一范式。更何况 NodeParam 这套声明式参数 Schema （name/label/ptype/default/min/max/step/choices/unit/tooltip，面板自动生成）比对方的 bindFilter(int, IEditControl*, Type) 手工绑定更现代。这一层不需要重做。
结论二：真正的差距是四条「闭环」没闭上。
① 数据闭环 —— 过杀/漏杀只是脑子里的印象，平台上没有沉淀（缺五态标记、缺难例转化）；
② 参数闭环 —— 训练参数散在 training/、classification/，推理过滤只有单点阈值，没有统一的「训练/增强/推理」三组参数页；
③ 评估闭环 —— 模型产生后没有「模型管理 + 效果报表」，评估结果（ROC / 概率分布 / 混淆矩阵）无法按模型归档对比；
④ 编排闭环 —— 训练/推理是同步阻塞调用，没有任务队列，长任务时界面被占住。
结论三：现场最痛的两个点，iCogtiveFlow 已经用产品化手段回答过了。
你们现场是凹点过杀 + 封印贯穿漏检 并存。对方的答案分别是： 「过杀」是一等公民标记（与漏杀并列，可统计、可回看、但不进训练集），以及 推理结果可直接"转成标注"（Convert Label / Mask To Label）形成难例回流。 这两件事恰好是当前 DL Studio 完全没有的，也是本路线图的一期重点。

2.1 关键手法：用「说明书 × 二进制」互证

说明书回答「做什么、为什么」，二进制回答「有哪些、叫什么」。两者一交叉，很多原本要靠猜的设计就落地了。举三个实例：

问题说明书给的二进制给的合起来得到的结论
标记体系到底几态？ P32：「可以进行 [正常]、[过杀]、[漏杀]、[存疑] 四种标记，该标记不影响训练，只做标记使用」 按钮名 btnNormal / btnOverkill / btnEscape / btnDoubt，四个工具里都出现 就是四态+纯管理用途。V3 里推测的第五态 "Train" 其实是数据集归属，不是同级标记 —— 本报告已修正
掩膜到底是什么？ P29：「掩膜限制了工具处理的区域，即训练时不会对掩膜区域采样，但推理阶段会采样」 框架类 MaskPattern 与 LabelPattern 成对出现，两个工具都有 MaskPattern 掩膜是训练/推理不对称的一等数据。分割场景下语义是"限制学习范围"，不是"忽略结果"
工具之间的共性有多强？ P21：「由于 Ai 工具具有相似的工作界面，接下来选取 2D 分割工具进行举例」 Segment2D / Classify2D / AnomalyDetect2D 三者的共享外壳完全一致，差异只有数据类与消息名 存在一个明确的工具插件框架。这决定了我们的节点基类要扩展成什么样（见第 4 章）

4.1 由此得出的「工具规格」

一个工具 = 1 个节点类型 + 1 份参数 Schema + 2 个任务处理器 + 1 套结果结构 + 1 个标注类型声明。 DL Studio 的 Node 基类目前只有前三项的雏形，建议扩展为：

class ToolNode(Node):
    """AI 工具节点的统一外壳（框架提供，工具只填自己特有的部分）。"""

    # ---- 身份（已有）----
    node_type      = "cls_infer"        # 唯一类型名
    display_name   = "分类推理"          # 显示名
    category       = "算法"
    source_types   = ("2D",)            # 新增：本工具接受的图源类型

    # ---- 参数：三组，而不是一坨（新增分组）----
    PARAMS_TRAIN   = [...]              # 训练参数：epoch / batch / 网络大小 / 分块 / 采样密度
    PARAMS_AUGMENT = [...]              # 增强参数：缩放/平移/旋转/亮度/对比度/高斯噪声/翻转
    PARAMS_INFER   = [...]              # 推理参数：8 维阈值区间 + 排序 + 最大检测数
    PARAMS = PARAMS_TRAIN + PARAMS_AUGMENT + PARAMS_INFER   # 让编辑器仍能平铺生成

    # ---- 标注契约（新增）----
    label_kind     = "mask"             # mask / rect / rotbox / point / tag
    supports_mask  = True               # 是否有掩膜层（训练不采样 / 推理采样）

    # ---- 生命周期（新增）----
    def train(self, ctx) -> None: ...   # 训练，向队列汇报进度
    def infer(self, frame) -> Frame: ... # 推理（现有 run 就是它）
    def convert_result_to_label(self, frame) -> None: ...   # 难例回流：结果 → 标注/掩膜
为什么这样切：iCogtiveFlow 把「参数管理 / 标注管理 / 模型管理」做成三个平行页签， 而工具之间的差异恰好落在这三处。我们把它显式声明到节点上，就能让 ui/flow_editor.py 的参数面板和 ui/annotation_toolbar.py 的工具栏 按同一份 Schema 自动适配所有工具，而不是每加一个工具就改一遍 UI。

5.1 项目与流程配置

iCogtiveFlow 工程 = 一个目录；进入「流程配置」在画布上拖节点连线（说明书 2.3.1/2.3.2、3.2.1）。 图片工具节点在流程里承担数据入口，AI 工具节点必须上级链接图片工具（P27）。
工程数据另存于 iCogtiveFlow.db（SQLite，objects 表存序列化的 Project，singles 存 $NextId / $currentProjectId / $lastTaskOrder 等游标）。
DL Studio 现状 已具备 flow/ DAG 引擎 + ui/flow_editor.py（拖拽/连线/参数面板/保存加载/单图运行）； core/project_manager.py 管项目目录，架构文档已规划 projects/<项目>/flows/。
差距 流程画布上的"数据入口"约束没做（现在可以连出非法拓扑而不报错）；时序游标 $lastTaskOrder（任务序号）无对应物。
规格要点 ① 节点声明 source_types，连线时校验"算法节点必须能追到数据源节点"，非法连接直接拒绝并提示； ② 方案 JSON 补 version 字段与向后兼容读取（架构文档第五章已列为配套功课，尚未落地）。

5.2 图片工具（Crop / TrueCrop / DiskImage）

iCogtiveFlow 作为流程里的数据节点：DiskImage（本地磁盘，设定图源类型与 Group Size）； Crop / TrueCrop（裁剪，说明书 2.4.2 图像裁剪工具）。 强调「先用裁剪工具或在算法工具里调 ROI，可以减少训练/推理的时间占比」（P63）。
DL Studio 现状 flow/nodes/basic.py 有文件源与基础预处理；ui/crop_tool.py（296 行）是现成的循环裁剪工具， 但没有节点化。
差距 裁剪仍是 UI 工具，不是流程节点；缺"把当前图的 ROI 一键套用到整个列表"（对方 P53 有此功能）。
规格要点 ① 新增 CropNode，内部复用 ui/crop_tool.py 的裁剪逻辑，参数 x/y/w/h、 支持"按像素/按百分比"两种输入；② ROI 批量套用：Frame.meta["roi_locked"] 机制， 列表级操作写一次即可对所有图生效；③ ROI 与裁剪的关系要在 UI 上讲清楚（裁剪改数据，ROI 只改推理范围）。

5.3 AI 工具工作界面（三模式 / 四图层 / 光标信息）

iCogtiveFlow 操作模式二选一：控件编辑模式（可操作裁剪区/ROI/掩膜/标注）与基础模式（仅缩放拖动）。
四个显示开关（表 2-4）：掩膜 / 标注 / 结果 / 可能性图——后者是推理概率热力图， 「越接近红色越重要，越接近蓝色越不重要」。
图片信息栏（表 2-8）：WH 分辨率、XY 鼠标坐标、RGB 像素值、 已标注 数量、已检出 数量、耗时 推理耗时；另有可显隐的 Loss 曲线框。
DL Studio 现状 部分 core/label_overlay.py + core/mask_overlay.py 已拆出叠加层； ui/heatmap_analyzer.py 有热力图；inference/predictor.py 已能出耗时； Grad-CAM 已能出图（208 张 BMP 的历史产出）。
差距 ① 图层是散的，没有统一的图层开关条（掩膜/标注/结果/可能性图 四开关）；② 没有"控件编辑 vs 基础"模式切换； ③ 光标信息栏缺（XY/RGB 实时取值、已标注/已检出 计数、耗时）； ④ 热力图目前是"事后分析"而非"实时图层"。
规格要点 ① 在画布组件上收口一个 LayerToggles（四布尔），由 Frame.result 驱动渲染； ② 推理耗时写进 Frame.result["infer_ms"]，与统计面板共用（见 5.10）； ③ "可能性图"和我们的 Grad-CAM 是同一诉求，统一叫热力图图层，做成可切换 overlay 而不是单独窗口。

5.4 标注体系（掩膜 / 标注 / 智能标注）

iCogtiveFlow 绘制工具（表 2-5）：线 / 矩形 / 圆椭圆 / 多边形 / 橡皮擦 / 多边形橡皮擦 / 智能标注 / 二值化自动识别（按阈值区间选区域，手动或自适应）/ 区域反转 / 删除选中 / 清空 / 撤销恢复。
智能标注（表 2-6/2-7）：AI 先自动画，再由参数区间过滤——网络大小（仅 Tiny）、采样密度、 灰度阈值、分数阈值、面积阈值、宽度阈值、高度阈值、角度阈值、排序次序，逐个给上下限。
标注管理（表 2-12）：刷新 / 多选合并类别 / 增删 / 上下移 / 全选 / 自定义颜色； 另有标注统计栏（类别、长宽、面积，点行可放大定位）。
DL Studio 现状 较好 annotation/：画笔/多边形/线条/橡皮擦、LabelMe 兼容 JSON、斜线纹理叠加、 标注块统计表（面积/周长/灰度/半径）、版本管理、SAM 辅助标注（sam_assist.py，能力上强于对方的智能标注）。
差距 ① 缺二值化自动识别（阈值区间直接生成掩膜/标注）；② 缺区域反转与多边形橡皮擦； ③ 缺类别合并（多选合一）——现场"同一缺陷多种叫法"历史数据整理时很有用； ④ 掩膜层与标注层在概念上没分开（对方是两套独立数据 + 不对称采样语义）。
规格要点 ① 掩膜独立成 mask 数据集（与 label 并列），并在训练采样处实现 "掩膜区不采样、推理不屏蔽"；② 补二值化一键生成（阈值区间 + 手动/自适应两模式）； ③ 标注管理加"合并类别"（含把合并映射写进版本记录，可回溯）。

5.5 参数管理（训练 / 增强 / 推理 三组）

iCogtiveFlow 训练参数（表 2-9）：训练轮数 / 训练批次 / 网络大小（小中大） / 模型（迁移基座）/ 分块（滑窗大小 + 步长）/ 图像块 / 采样密度。
原文关键经验：网络大小"可以根据 CT 需求、过杀率、漏检率等指标进行平衡选择"； "较大缺陷可设置较大的块，较小的缺陷可设置较小的块；小图像优先整图训练，效果优于分块"。
增强参数（表 2-10）：缩放 / 放大 / 平移 / 长宽比 / 裁剪 / 旋转 / 增强亮度 / 对比度 / 对比度反转 / 高斯噪声 / 翻转，且悬停即可预览增强效果（图 2-42/2-43）。
推理参数（表 2-11）：数据集（所有/测试集/训练集）+ 模型 + 八维阈值区间 （分数 / 面积 / 宽度 / 高度 / 角度 / 灰度 / 半径 / 中心半径）+ 排序 + 最大检测数。
DL Studio 现状 部分 training/augment_config.py（三档增强）、classification/threshold.py + ui/threshold_panel.py（阈值）、ui/infer_params.py（推理参数）、 training/multiview.py（多视图）、分类超参在 classification/trainer.py。
差距 ① 参数分散在各模块，没有统一的"工具参数页"，换个工具就要去别的地方找； ② 推理过滤只有分数等少数几维，缺面积/宽/高/角度/灰度/半径/中心半径； ③ 缺"最大检测数"；④ 增强参数不能所见即所得预览；⑤ 缺"分块/图像块/步长"的显式参数（推理侧有 tiled 但训练侧不完整）。
规格要点 ① 参数统一走 NodeParam 声明，按 PARAMS_TRAIN / PARAMS_AUGMENT / PARAMS_INFER 三组渲染成三个折叠区（对应对方的三个配置页）； ② 推理过滤扩展成八维区间 + 上限，每维一个 [min, max]，空值=不过滤； ③ 增强参数面板加悬停预览（用当前图实时跑一次增强，显示在缩略图上）； ④ 分块参数显式化：tile_size / stride，并在 UI 上给出"块大小 vs 缺陷尺度的建议"提示。

5.6 数据集划分

iCogtiveFlow 训练集 / 验证集 / 测试集，验证集"推荐不设置"（P42）；常见比例 6:2:2 / 14:3:3 / 8:1:1； 操作是右击缩略图 → Change Set → 批量划分（可多选，图 2-48 / 3-8）。
两条工程经验：样本尽量均衡，不均衡时用"样本生成 / 图像复用"补； 分割工具里训练集可以是 OK 图，也可以是 NG 图（P64）。
DL Studio 现状 部分 训练器里能按比例切分，classification/recommend.py 会给数据建议。
差距 ① 划分没有可视化的批量操作界面（现在多是训练时按比例随机切）； ② 没有"这一张属于哪个集合"的显式状态，也就无法在列表里按集合筛选；③ 缺"OK 图也能进训练集"的显式支持说明。
规格要点 ① 图片条目增加 split 字段（train/val/test/none），持久化进项目 JSON； ② 列表支持多选 + 右键"设为训练/验证/测试"；③ 工具栏显示当前比例并可一键按比例重排； ④ 训练时严格按 split 取值，不再随机切（保证可复现）。

5.7 图像列表筛选（表达式引擎）

iCogtiveFlow 筛选条件可自定义表达式（图 2-39）：字段（如"结果类别"）+ 条件（contain / !contain） + 值 + 连接词（AND / OR），带语法检测； 例：「筛选结果为存在 Class1 并且 结果分数大于 0.5 的图像」（P34）。 条件可新增/删除/编辑，默认条件不可删；列表表头右键可增删显示列。
DL Studio 现状 缺 列表目前按文件名/时间等固定项排序，没有表达式筛选。
差距 这是难例挖掘的入口：现场要看"所有被检出但人工判为过杀的图"、"所有分数在 0.3–0.5 的图"， 没有筛选就只能靠肉眼翻列表。
规格要点 ① 定义筛选字段表：文件名 / 标记（正常·过杀·漏杀·存疑）/ 数据集(split) / 结果类别 / 结果分数 / 检出数量 / 标注数量 / 图像尺寸 / 推理耗时 / 是否有标注；
② 表达式 = 三元组列表 [(字段, 条件, 值)] + 连接词，条目式 UI（不做自由文本解析，避免注入与语法坑， 但提供"语法检测"等价物 = 字段/条件合法性校验）；
③ 筛选结果直接驱动列表与"批量标记/批量转标注"操作 —— 这是 5.8 的前置。

5.9 模型管理与结果报表

iCogtiveFlow 模型管理（表 2-13）：模型列表 + 控制栏（刷新 / 导入 / 导出 / 删除）+ 模型效果报表； 选中模型，下方报表随之变化。点结果右侧可打开报表页面，可"查看整个项目的结果并添加工程相关信息以及检测需求与结果"（P42）。
验证结果查看（表 3-1）：模型信息（耗时、损失率）/ 概率分数分布图 / ROC / 分割结果（LTRB 矩形）。 附带配置键 TrainModelId / InferModelId / InferModelType / ChangeInferModel / preModelId、临时模型 /TempModel.net。
DL Studio 现状 部分 classification/eval.py 与分割评估指标（10 指标，已产出报表 HTML）、 classification/gradcam.py、tools/compare_models.py（模型对比）、 tools/eval_seg_metrics.py。
差距 ① 评估是"脚本产出 HTML"，没有模型仓库视图（哪个模型对应哪份报表、谁更优）； ② 缺概率分数分布图与 ROC 的常规化输出；③ 缺"把工程信息 + 检测需求 + 结果"写进同一份报表的做法。
规格要点 ① 建"模型仓库"：每次训练产出一份 models/<项目>/<工具>/<时间戳>/（权重 + 超参 + 训练曲线 + 评估指标 + 数据划分快照）， 列表可对比、可导出、可删除；
② 报表模板固定为：模型信息（耗时/损失）+ 概率分布 + ROC + 指标表 + 数据/需求元信息（谁、什么料号、什么 KPI 目标）；
③ 推理时选模型，键名对齐 infer_model_id，避免"选了模型但实际跑的是默认权重"。

5.10 任务队列与训练曲线

iCogtiveFlow 训练/推理都是任务队列里的任务："点击训练按钮，会在任务队列中添加训练任务，当执行到该任务时， 会弹出实时更新的 Loss 曲线，训练完成后 Loss 曲线框自动关闭"（P44）。 Loss 曲线判读经验："鱼缸曲线的下降阶段是欠拟合，水平阶段是可以用于检测的"（P57）。 任务协议侧有 CHhTask / CHhTaskControl（get / put / start / stop）与 TaskBase.checkState() / finishCode()（可编程归因失败原因）。
DL Studio 现状 部分 有实时 loss/accuracy 曲线、断点续训、中途停止；但训练/推理是同步调用（架构文档诊断： "无方案概念…硬编码调用链"，批量推理已迁到 flow/batch.py）。
差距 ① 没有队列，多个任务只能串行等；② 长任务期间 UI 被信号回调占住； ③ 失败原因靠日志文本，没有结构化的失败码（对方有 finishCode()）。
规格要点 ① 引入 TaskQueue（单消费者线程 + 任务对象：kind / params / state / progress / finish_code / error）；② 训练/推理/批量推理全部入队， UI 只订阅进度信号；③ 失败码枚举化（OOM / DATA_EMPTY / NO_LABEL / CKPT_MISSING / USER_STOP…）， 对应到可读提示与处置建议。

5.11 工具链接（级联）

iCogtiveFlow 第 10 章：「目标检测、分类、分割都可以链接到其他的工具」；链接前提是上级工具已完成推理、能提供图源； 核心机制："分割工具和目标检测工具推理后可以将分割结果作为 ROI 或掩膜传递给下工具。 若结果存在多个，则将会在下工具的输入上增加图像的数量"（P94）。
三个官方范例：分割+分类（判 NG/OK）、分割+目标检测（大范围先筛再计数）、 目标检测+分割（先定位限制 ROI 再分割，减少耗时）。
DL Studio 现状 框架已支持 DAG 天然能串联多节点（seg_filter.py 已是"分割结果过滤"节点）。
差距 缺语义层面的"结果→ROI / 结果→掩膜"标准转换：现在要自己写胶水；也缺"多结果 → 拆成多个 Frame"的约定。
规格要点 ① 在 Frame 上补两条标准出口：frame.roi_from_result(idx) 与 frame.mask_from_result(idx)；② 提供 ExpandResultsNode：一个 Frame 里 N 个结果 → N 个子 Frame（对齐对方"增加图像数量"的行为）；③ 在流程编辑器里给出三个"官方范例模板" （分割+分类 / 分割+计数 / 检测+分割），降低上手成本。

5.12 图源类型（2D / 3D / 混合 / 多图 / 对比）

iCogtiveFlow 第 9 章：2D 单图、2D 多图（一组同物体多张）、3D 单图（高度图以点云形式展示， 带颜色映射范围/上下阈值/3D 立体视图）、2D+3D；另有对比分割/对比分类（两组图：标准图 + 检测图，Group Size=2）。
工程建议："3D 相机采集的分辨率比较大，若直接加载…可能因内存占用造成软件崩溃，建议在 3D 工程前先进行截图操作"（P90）。
DL Studio 现状 部分 training/multiview.py + ui/multiview_preview.py（多视图）、 ui/mixed_viewer.py + classification/dual_model.py（灰度+高度图双模态， 对应 ClassifyMixed 的思路）、flow/nodes/visualize.py 有 heightmap_rainbow。
差距 ① 缺对比类（标准图 vs 检测图）——对孚能"同料号同位置批次比对"非常实用； ② 3D 侧只有彩虹图叠加，没有点云视图与阈值条交互；③ 没有"先降采样/截图再加载"的内存保护。
规格要点 ① 新增 CompareNode（输入两个 Frame：基准 + 待检，输出差异区域）作为对比分割/分类的共用底座； ② 大图内存保护：Frame 增加 load_scale 元信息，列表预览强制降采样； ③ 3D 点云视图列为 P2（现场主要是 2.5D 三通道，优先级低于 ①②）。

6 P0 专章：五态标记与难例闭环

为什么是 P0：现场同时存在「凹点 AI 过杀」与「封印贯穿人工漏检」。这两件事在现有平台上都没有沉淀—— 今天的过杀判断，明天换个人看就没了；今天发现的一条漏检，不会自动变成明天的训练数据。 对方的做法是把这两件事直接做进产品。

6.1 标记体系（证据确凿，可直接照规格实现）

说明书 P32 原文：「iCogtiveFlow 支持人为对图片进行标记，可以进行 [正常]、[过杀]、[漏杀]、[存疑] 四种标记， 该标记不影响训练，只做标记使用。单击选中图片然后单击标记按钮为图像进行标记，点击清空按钮可以清空当前图像的标记， 图像标记信息可以在标注管理一栏查看。」

二进制侧对应四个按钮：btnNormal / btnOverkill / btnEscape / btnDoubt （三个工具 dump 中均出现，说明在框架层）。

最关键的一句是"不影响训练"。这解决了我们一个长期隐患：如果把「过杀」当成一个类别塞进训练集， 模型会学到"过杀长什么样"这种无意义的概念。标记是质检口径的沉淀，标签才是训练数据，两者必须分开。

6.4 难例闭环：把"看走眼"变成"下一轮训练集"

对方的三个动作（字符串证据 Convert Label / Mask To Label / Recrop images， 以及提示语 "Successfully converted the selected detection results into annotations"）：

动作语义我们的对应规格
Convert Label 把推理检出的框/区域直接变成标注 选中若干"被检出"的图 → 一键"结果转标注"。这正是把过杀（AI 检出但人判不是缺陷） 或漏检附近的真实缺陷快速变成训练数据的手段：前者提供负样本，后者提供正样本。
Mask To Label 把掩膜转成标注（或反向） 掩膜与标注的正反向转换。现场意义：先用二值化/智能标注圈一大片当掩膜，人工微调后转成正式标注。
Recrop images 按当前 ROI/裁剪设定重新裁剪整批图 改一次 ROI 全员生效，避免逐张重裁（接 5.2 的 ROI 批量套用）。
把它们串成闭环（这是本路线图最想要的成果）：
推理 → 标记过杀/漏杀 → 筛选出这批图 → 结果转标注（过杀→负样本/修正框；漏杀→补正样本） → 重新划分数据集 → 增量训练 → 用模型报表对比新老模型在同一测试集上的过杀率/漏检率。
这条链闭上之后，"过杀率 47%" 这种数字才会变成可管理的日常动作，而不是每次重头手工统计。

9 不该照抄的部分

对方的做法为什么不照抄
C++ / Qt 单体桌面 + 每工具一个 dll 他们这么做的历史原因是算法库（IAL/Metrology）本就是 C++ 视觉底座，需要与标定、测量共用内存与句柄。 我们是 PyTorch 生态，Python 侧的迭代速度与模型生态是核心优势。用 dll 换来的隔离性，我们用 Python 包 + 节点注册替代即可。
手工参数-控件绑定（bindFilter(int, IEditControl*, Type)） 我们要维护 20+ 个工具，手工绑定会导致每加一个参数就要改三处。 现有声明式 NodeParam Schema 让面板自动生成，是更优解，保持。
"验证集推荐不设置" 对方的模型相对固定、数据量小，简化流程合理。但我们的场景需要可信的泛化评估（客户 KPI 要对簿）， 验证集必须保留；不过可以采纳其精神——测试集要固定且不许参与调参。
训练侧也走 dll + LibTorch 训练用 Python/PyTorch 更灵活（自定义 loss、增强、Grad-CAM 都在 Python 侧）。 仅在部署推理上做 Turbo 化（我们已有 ONNX / TorchScript / TensorRT 多后端，方向正确）。
软件多开（multiInstances） 是单进程架构下的权宜之计。我们天然可以多进程/多项目，不需要照搬目录结构。
整体 8 GB 的运行时依赖 对方的 torch_cuda 1.4 GB + nvinfer 440 MB 全量随包。我们应按项目按需安装后端，避免交付包失控。

10 待拍板

#问题我的建议
1一期是否就按本报告的 6 项启动？（标记 → 筛选 → 转标注 → 八维过滤） 建议启动。这 6 项构成一条完整闭环，能立刻回答"我们现在的过杀率是多少、哪些图需要回流"。
2"过杀/漏杀"的判定基准是什么？ 需要你定义：以人工复判为准，还是以客户标准为准？这决定标记的语义边界（这是阈值与口径类问题，我不擅自定）。
3标记是否要带"理由/备注"字段？ 建议带（可选填）。现场"这个凹点为什么算过杀"的经验是最难传承的资产。
4八维过滤的默认值怎么定？ 建议先按"只开分数 + 面积"两项上线，其余默认关闭（空=不过滤），避免一次引入太多参数把操作员吓住。
5是否要做"异常检测"（无监督）？ 建议做，且优先给 3/4 号机（P187 来料好）——正常样本多、缺陷样本少，正是无监督的主场。
6对比类工具（SegmentCP）的优先级 建议放四期。它对"同料号同位置批次比对"很有价值，但需要先有稳定的 ROI 与对齐机制。
