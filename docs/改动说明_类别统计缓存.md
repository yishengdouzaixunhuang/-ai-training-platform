# 改动说明：类别统计结果缓存（B 项）

**日期** 2026-11-10 · **文件** `ui/class_table.py`、`ui/main_window.py`、`tests/test_counts_cache.py`（新增）
**改动量** +165 / −8

---

## 一、问题

上一轮（`docs/改动说明_类别统计去重.md`）把「切换工程时算 2~3 次」压到 1 次，剩下的
`_compute_counts()` **每次调用都要把工程里所有标注文件重新看一遍**：

| 工程 | 图/组数 | 一次 `_compute_counts()` |
|---|---|---|
| 极片 | 1002 张 | **131 ms** |
| 20260604 | 1316 张 | 168 ms |
| 眉山中航（另一台机器） | 2001 张 | 500 ms+ |

它被三处触发：打开工程、切回工程、按「刷新」。而**其中 99% 的文件一个字都没变**。
上一轮审核提的 B 项就是这件事，并特别点名一条：缓存键只挂 `images/` 的签名会漏掉
`class_labels.json`（分类工程的类别真源），漏了就是"改了类别数字不更新"，
比数字算错更难被发现。

## 二、改了什么

### 1. 工程级「结果缓存」，指纹没变就直接返回

`_compute_counts()` 进来先算一次工程内容指纹（`_counts_signature()`），指纹相同就
直接返回上次的结果。指纹构成：

| 项 | 为什么必须在里面 |
|---|---|
| `tuple(labels)` | 调用方临时改了类别表（还没落盘）也得重算 |
| `images/` 扁平快照 | 加图 / 删图 / 换图；**labelme JSON 也在这里**（真实工程就是 JSON 与图并排） |
| `images/<类别>/` 子目录快照 | 分类工程的「空集」按类别目录算，不上一层 |
| `annotations/` 扁平快照 | `_mask.png`、**`class_labels.json`** 都在这里 |
| `train_test_split.json` | 划分变了，train ↔ val 的数字必须跟着变 |
| `project.json` | 类别、视图数等工程元信息 |
| 根目录 `class_labels.json` | 少数工程把类别真源放根上（双保险） |

快照来自 `os.scandir`（Windows 上 FindFirstFile 一次带回全部属性），摘要用
**与顺序无关**的累加 hash —— scandir 的返回顺序不做保证，按顺序拼字符串算哈希
会把"内容一样"判成"变了"，缓存当场失效。

### 2. 命中时连 `_split_bases` 一起还原

`_split_bases` 是 `_compute_counts()` 的**副作用**（点数字格子过滤图片列表要靠它）。
命中缓存就 `return` 而不还原，过滤会变成"点了没反应" —— 这种静默失效比慢更糟。

### 3. 「刷新」按钮绕过缓存

新增 `invalidate_counts()`；`ClassTableView.refresh()` 与
`MainWindow._refresh_class_stats()`（「刷新」按钮的真实落地路径）都先作废再重算。
理由：用户点刷新就是明确要求重新统计，命中缓存会让按钮看着没反应；也留了一条
"内容改了但 mtime/大小没变"时的自救通道。

### 4. 读不了目录时**不进缓存**

`_dir_index()` 返回 `None` 表示目录在但读不了（网络盘断连 / 权限 / 被独占）。
此时 `_counts_signature()` 返回 `sig=None`，**既不查缓存也不写缓存** ——
宁可重算一次，也不能把"读失败"当成"文件都没了"写进缓存。

### 5. 缓存上限 8 个工程，FIFO 淘汰

`_COUNTS_CACHE_MAX = 8`。每个工程的 `counts` 是十几个元组、`split_bases` 是一批
字符串，常驻开销可忽略；不设上限才会在长时间换工程时涨上去。

## 三、验证

### 1. 耗时（`_probe_counts_cache.py`，只读真实工程）

| 场景 | 改前 | 改后 |
|---|---|---|
| 极片 同工程再算 | 131 ms | **5.0 ms** |
| 极片 切走再切回 | 128 ms | **4.0 ms** |
| 20260604 同工程再算 | 168 ms | **3.6 ms** |
| 混合分类 切回 | 102 ms | **2.8 ms** |
| Classify 同工程再算 | 87 ms | **1.2 ms** |
| 极片 冷算（第一次，无缓存） | 353 ms | 397 ms（+13% 指纹开销，只付一次） |

### 2. 数字对不对（这是关键）

- `_probe_counts_cache.py` 直接读**表格控件里显示的文字**，与 `_compute_counts()`
  返回值逐项比对：极片 14 行、Classify 2 行，**不一致 0 行**，且与改前基线完全相同
  （极片 Ak 54/6/7/0、\_\_ignore\_\_ 223/28/27/0；Classify NG 74/14/2/0、OK 119/17/2/0）。
- `_probe_counts_ui.py` 走**真实 MainWindow**：打开极片 → Classify → 切回极片 →
  再切回 Classify，每个工程切回后的表格文字与首次**完全一致**（`ok: true`）。
  首次打开 1311.7 ms / 切回 680.9 ms（含图列表构建，统计本身只占 4 ms）。

### 3. 该失效的时候一定失效（`tests/test_counts_cache.py`，13 条）

| 用例 | 钉住的行为 |
|---|---|
| 数字与划分正确 | train / val / test 归桶 |
| 命中缓存不重扫 | 第二次 `scan_labels` 调用数 = **0** |
| 命中时还原 `_split_bases` | 过滤数据跟着回来 |
| 改标注 JSON 会失效 | 多画一个类别，数字跟着变 |
| 加图会失效 | 新增带标注的图 |
| 改划分会失效 | train → test 立刻反映 |
| 改类别顺序会失效 | 缓存不能按旧索引返回 |
| **改 `class_labels.json` 会失效** | 审核点名的那条 |
| 类别目录加图会失效 | 分类工程「空集」 |
| 刷新按钮绕过缓存 | `invalidate_counts()` 后确实重扫 |
| 目录读不了不缓存 | `sig is None` 且缓存保持空 |
| 切回工程命中缓存 | 重扫 0 次 |
| 缓存有上限 | FIFO 淘汰 |

## 四、请重点核对

1. **指纹只看"内容签名"，不看"谁改的"** —— `scan_labels` 用的也是 `mtime_ns + size`
   这套口径，所以这里没有引入新的盲区，但有同一个已知弱点：**SMB 网络盘上如果时间戳
   精度只到 1 秒、且改完大小没变**，两套缓存都会漏。兜底是「刷新」按钮（已强制重算）。
2. **冷算 +13%**：指纹要多扫一遍 `images/`（1002 个名字约 40ms）。第一次打开工程时付
   这一次，之后每次省 120ms+。如果认为首开更敏感，可以把 `_subdirs_sig` 改成"仅分类
   工程才算"，但那样要判断工程类型，代码复杂度换 20ms，我没做。
3. **`_split_bases` 存的是 set 的副本** —— 命中时 `{k: set(v) for ...}` 复制一层，
   防止调用方改到缓存本体。若将来有人往 `bases_for()` 的返回值里塞东西，这里要重审。
4. **顺手发现但没修的旧问题**：分类工程「空集」的比对区分大小写 ——
   `mapping` 键是 `images/ok/a.bmp` 而类别名是 `OK` 时，同一张图会被算成"空集"，
   数字偏大。本机现有工程都是扁平 `images/`（不经过这段），只有 ImageFolder 布局的
   工程会碰到。要不要修等你拍板（改成大小写不敏感比对即可，但会改变那些工程现在的数字）。
