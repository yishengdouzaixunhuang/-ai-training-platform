# 列表构建异步化 · 改动说明（供审核）

**提交** `git log --grep="列表构建异步化"` · **日期** 2026-11-06 · **文件** `ui/main_window.py`（唯一改动的代码文件）
**规模** +87 / −23 行（净 +64）

---

## 一、为什么要改

打开大图工程（眉山中航，2001 张图）时，`_filter_images` 在主线程同步构建 2001 行数据：

```
标注统计预热完成，列表回填 8626 ms
```

**这 8.6 秒里界面完全僵住**，进度条刚走到 100% 就卡死，用户会以为点坏了。
用户反馈的「打开工程很卡」，真凶就是这一段。

## 三、拆分后的结构

| 方法 | 运行线程 | 职责 | 行数 |
|---|---|---|---|
| `_filter_images(text)` | 主线程 | 入口：代次+1、快照 UI、起线程，**立即返回** | ~20 |
| `_snapshot_filter_ctx(text)` | 主线程 | 把 8 个来自 UI 的值拍成 dict | ~40 |
| `_filter_rows_body(gen, ctx, t)` | **后台 daemon 线程** | 目录扫描 + 行记录组装，产出 `rows` + 统计 | ~440 |
| `_on_filter_rows_ready(...)` | 主线程 | 渲染 + 更新各计数条（原函数尾部的 UI 代码） | ~80 |

**关键点：`_filter_rows_body` 的方法体几乎就是原 `_filter_images` 的中间部分**，
git diff 之所以只有 110 行，是因为它识别成了块移动，实际逻辑一行没删。

## 四、逐条改动清单（审核重点）

### 4.1 新增信号

```python
# 后台把列表行数据算好后回主线程渲染（代次, payload, 起始时间戳）
filter_rows_signal = pyqtSignal(int, object, float)
```

用 `object` 传 payload（dict + list），避免 Qt 容器类型转换开销。

### 4.2 12 处 UI 控件访问 → 改读快照

后台线程不能碰 Qt 控件，所以凡是后台要用的、来自 UI 的值，全部在主线程先读出来。

| 原代码（行号） | 改成 | 原因 |
|---|---|---|
| `self.image_list_widget.setRowCount(0)`（4266） | **删除** | 清空由 `_render_page` 负责，它自己会先 `setRowCount(0)` |
| `self.split_filter.currentText()`（4272） | `ctx["split"]` | 控件不能跨线程读 |
| `self.annotated_check.isChecked()`（4273） | `ctx["annotated_only"]` | 同上 |
| label_filter 下拉同步块 12 行（4276–4291） | **整块移到** `_snapshot_filter_ctx` | 它是 UI **写**操作（clear/addItems），必须留主线程 |
| `self.recent_check.isChecked()`（4316） | `ctx["recent"]` | 同 4272 |
| `self.recent_check.isChecked()`（4346） | `ctx["recent"]` | 同上 |
| `self.pred_count_spin.value()`（4579） | `ctx["pred_thr"]` | 同上 |
| `self.pred_op_combo.currentText()`（4580） | `ctx["pred_op"]` | 同上 |
| `self.pred_count_spin.value()`（4581） | `ctx["pred_thr"]` | 同上 |

> 核对方法（可复现）：
> ```bash
> awk '/def _filter_rows_body/,/def _on_filter_rows_ready/' ui/main_window.py \
>   | grep -E "self\.(split_filter|annotated_check|label_filter|recent_check|pred_count_spin|pred_op_combo|image_list_widget)"
> # 输出应为空
> ```

### 4.3 `self._all_images` → 局部 `images`（9 处）

原代码里有一行 `self._all_images.sort(key=_json_mtime, reverse=True)`（按最近标注排序）。
如果后台线程直接改这个列表，主线程同时在用会出问题。

改法：`ctx["images"] = list(self._all_images)`，后台排序的是**副本**，
`self._all_images` 保持原顺序（每次刷新都重排一次，行为一致）。

### 4.4 `self._filtered_data` → 局部 `rows`

后台把行记录 append 到局部 `rows`，算完通过信号交给主线程一次性赋值：

```python
self._filtered_data = payload["rows"]
```

避免主线程在后台还在写的时候读到半截列表。

### 4.5 函数尾部的 UI 更新（69 行）搬到回调

`stats_summary.setText(...)`、`list_status.setText(...)`、`_update_selection_count()`、
`_update_hm_section_visibility()`、`_sync_mark_filter_label()`、`_refresh_img_info()` 等
**全部原样保留**，只是执行时机从「构建完立刻」变成「信号回调里」。

唯一改名：`_t_fi0` → `t_start`（作为信号参数传过来，用于 `_last_filter_ms` 计时）。

## 五、线程安全怎么保证

| 措施 | 说明 |
|---|---|
| 后台零 Qt 访问 | 已用上面的 grep 核对 |
| 共享数据只读 | `_pred_count`、`_img_scores`、`_mark_filter`、`_defect_filter`、`_filter_expr` 后台只读（`FilterExpr.evaluate` 是纯函数） |
| `_all_images` 用副本 | 见 4.3 |
| `_filtered_data` 最后一次性赋值 | 见 4.4 |
| 代次 `_filter_gen` | 连点筛选条件时，旧任务的结果被丢弃（两处判断：后台开头、emit 前各一次） |
| daemon 线程 | 关窗口时不阻塞退出 |

## 七、请审核者重点看这几处

1. **`_snapshot_filter_ctx` 的返回值是否覆盖全了**
   漏一个，后台就会 `NameError` 或读到旧值。当前 8 个键：
   `text_lower / split / annotated_only / label / recent / pred_thr / pred_op / images`

2. **`_on_filter_rows_ready` 里的 69 行 UI 代码是否与原版一字不差**
   （除了 `_t_fi0` → `t_start`）。这是最容易搬错的区域。

3. **代次判断的两处是否够**
   - `_filter_rows_body` 开头：进线程就发现过期 → 直接 return
   - `emit` 之前：算完才发现过期 → 不覆盖界面

4. **`_suppress_cell_change` 的时序**
   主线程入口设 `True`，回调末尾设 `False`。中间跨线程，期间若有别处读这个标志，
   会读到 `True`（即"正在批量更新，忽略单元格事件"）—— 这是期望行为，但值得确认。

5. **有没有漏掉的调用点依赖同步返回**
   已查全部 20 个调用点（搜索框、各筛选下拉、`refresh_list_signal`、删除/撤销后刷新等），
   没有一处紧接着读 `_filtered_data` 或 `image_list_widget.rowCount()`。
   ⚠️ 唯一需要留意的是 `_on_mask_stats_ready`：它原来在 `_filter_images` 之后
   读 `rowCount()` 恢复选中行，现在这一步在异步回调里，**行数可能还是旧的**。

## 十、审核意见处理记录（2026-11-06 第二轮）

审核提出 6 类问题，**全部核实成立、全部已修**（提交见 `git log --grep="审核意见"`）。
下面按她的编号逐条对应，含实测复现与验证结果。

### P0 打开工程后画布空白、列表无选中行 —— ✅ 已修

- **原因**：`_populate_image_list` 里 `selectRow(0)` 紧跟 `_filter_images("")`。
  异步化后该调用立刻返回，此刻表格里一行都没有（`item(0,0)` 是 `None`），
  `_load_image_by_index(0)` 在 `if item:` 处空转。
- **实测复现**（修前）：`列表行数 2001 / currentRow -1 / canvas None`
- **修法**：改打 `_pending_select_first` 标记，由 `_render_page` 尾部消费：
  - 先按 `canvas.current_image_path` 找回原行（原逻辑保留）
  - 找不到且有 pending 标记 → 选第 0 行
  - 锁定 → `selectRow` → 解锁 → **显式** `_load_image_by_index`（只加载一次，
    不靠 `selectRow` 的副作用，避免 20MP 图重复解码）
- **实测**（修后）：`currentRow 0 / canvas 已加载第一张 bmp`

### P1「列表很快出来、标注列逐步补齐」是错的 —— ✅ 已修（含更正说明）

**这条审核是对的，我之前的描述有误**：后台是**一次性算完 2001 行才 emit**，
中间不 emit 任何东西。真实表现是列表空 6.8 秒然后「啪」地全出现。

- **修法**：`_filter_images` 入口立刻在 `stats_summary` 显示
  「筛选中…（上次 N 行）」，不清空列表（避免闪一下 + 丢当前上下文）
- 结果到达后由 `_on_filter_rows_ready` 正常覆盖

### P1 搜索框没防抖 —— ✅ 已修

- 280ms 单发 `QTimer`，只有 `search_input.textChanged` 防抖；
  下拉框/勾选框不动（它们不会连发）
- **实测**：连打 4 个字符（间隔 50ms）→ 后台构建**只触发 1 次**

### P1 后台无异常兜底 —— ✅ 已修

- `_filter_rows_body` 包一层 try，原逻辑改名为 `_filter_rows_body_impl`；
  异常时也 emit 一个 `{"error": ...}` payload
- `_on_filter_rows_ready` 收到 error：复位 `_suppress_cell_change`、
  隐藏进度条、统计条显示「筛选失败」、状态栏显示具体异常
- **实测**：模拟后台抛 `RuntimeError` 后 —
  `_suppress_cell_change=False`、统计条「筛选失败」、
  状态栏「列表构建失败：RuntimeError: 模拟后台异常」、**再次刷新能回到 2001 行**

### P2 五处小问题 —— ✅ 全部已修

| 她指出的问题 | 修法 |
|---|---|
| `_filtered_data` 切工程后 6.8s 内还是上个工程的数据 | `_populate_image_list` 开头置 `[]` |
| `_split_map_cache` 挂 self，两个后台线程互踩 | 改成 `_filter_rows_body_impl` 内的局部 `_split_cache` |
| `_last_filter_ms` 读到上一轮的值，首次是 None 导致日志消失 | 日志挪到回调，`QTimer.singleShot(0, ...)` 延迟一拍打 |
| `_mv_group_count` / `_mv_mode_list` 后台写、主线程立刻读 → 多视图日志打错 | 塞进 payload（`mv_on/mv_meta/mv_groups/mv_note`），回调里用 |
| 只校验 `_filter_gen`，不校验 `_project_gen` → 切工程时旧线程把上个工程行渲进新工程 | payload 带 `project_gen`，回调里两个都校验 |
| L4131 的 `_suppress_cell_change = False` 紧跟调用后，把刚设的 True 抹掉 | 删除 |

### 关于「她列的第 5 条遗留问题其实不用担心」

**她判断正确**。`_on_mask_stats_ready` 的选中恢复确实不是问题（`_render_page` 尾部
会按 `canvas.current_image_path` 找回），真正没接住的是「当前没有图」的情况 ——
也就是 P0 那个根因。已由 `_pending_select_first` 一并解决，两件事合成一处修复。
