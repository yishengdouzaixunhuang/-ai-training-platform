一、结论摘要：它强在哪、我们缺什么

判断一：它不是"另一个训练工具"，它是算子流平台

我们 DL Studio 现在的形态是「任务型工具」——每个任务（分类/检测/分割/OCR）有独立的 数据集、训练器、推理入口。它是「平台型」——所有能力都是节点，节点连成 DAG， 训一个节点 ↔ 执行一个节点。 你已经有 flow/（Frame/Node/Registry/Runner/Flow）+ ui/flow_editor.py， 骨架方向是对的，差的是"节点种类 × 图源模态"这一层矩阵，以及节点目录/版本/结果这三套约定。

判断二：它的参数体系是我们最大的差距，不是算法

我们分类训练器的可调项是：epoch / batch / lr / optimizer / loss / dropout / weight_decay / 调度 / 增强开关（十来个）。 它单个分割节点是 52 个具名参数，而且分成四类职责清晰：

类别它有什么我们的现状
训练 Batch / Epoch / Capacity(网络容量) / PatchSize(图像块) / StepSize(步长) / ReceptiveField(特征尺寸) / ByPatch / DeviceId / Platform 有 epoch/batch/lr，缺滑窗与特征尺寸概念（大图必须靠它控显存）
增广 Flip / Rotate / ImageZoom / ImageZoomIn / ImageMove / ImageShear / ImageBright / Contrast / InvertContrast / GaussianNoise（各带 Switch） 有翻转/旋转/颜色抖动，缺"每个增广独立开关 + 悬停预览"
后处理 Score / Area / Gray / Contrast / AspectRatio / Width / Height / Angle 阈值 + MaxDetectCount / Density / Capacity 排序 基本空白——预测出来就直接用，没有可调过滤层
可视化 V 前缀：VCategory / VRadius / VCenterRegionRadius / VPredictSortOrder 无此概念——展示参数与业务参数混在一起

最值得抄的一条范式：所有过滤条件都是 {参数} + {参数}Switch 成对出现。 这样"这个条件启不启用"和"阈值多少"是两个独立维度，改阈值不会意外改行为。

判断三：它的"闭环"比我们完整——标注→训练→评估→难例回流

它的说明书里明确写了这个循环：

先标有代表性的部分样本 → 训练 → 用结果筛选（分数/面积/类别）→ 把结果导入标注 → 精细化修改 → 再训练

支撑这个闭环的是三个我们完全没有的功能：

  • 图像列表自定义筛选：字段 / 条件 / 值 / AND-OR 连接词，还能"语法检测"。可以筛出"结果含 Class1 且分数 > 0.5"的图 —— 这就是难例挖掘。
  • 图像人工标记四态：正常 / 过杀 / 漏杀 / 存疑，明确写"不影响训练，只做标记用"。
  • 模型效果报表 + 结果报表页：可直接填工程信息与检测需求/结果 —— 和你做 PPT 的活儿重合。

判断四：它的底层范式继承自 Cognex ViDi（这个映射很关键）

说明书「专业术语」一节里，讲"特征尺寸"用的例子是：根据发动机数量给飞机图片分类，特征尺寸就按发动机大小定。 这是 Cognex ViDi 的经典官方比喻；"采样密度""运行时采样（默认采样率 3）"也全部是 ViDi 的原术语。

所以它的技术底座 = ViDi 的"滑动窗口 + 特征尺寸 + 采样密度"范式，用现代深度学习重写，外面套一层 Flow 节点图。
这解释了两件事：①为什么它单个节点的参数那么多（ViDi 本来就是"调参换性能"的哲学）； ②为什么它推荐"验证集可以不设"（ViDi 体系里训练/测试二分就够了）。
对我们的含义：如果目标是复刻它的检测能力，核心不是换模型，而是把 ReceptiveField / PatchSize / StepSize / Density 这套"窗口采样"参数做成我们自己的配置层。

三、工程文件格式解剖

为什么这一章值得看：文件格式决定了"项目的可移植性 / 版本管理 / 出问题时能不能救回来"。 它的设计非常克制 —— 只有 2 张表，却装下了整个平台。

3.1 三个存储单元，同一套 schema

工程文件  {项目名}.isf           ← SQLite（WAL 模式）+ .isf-shm + .isf-wal + .isf.lock
节点文件  {节点名}/{节点名}.node   ← 同样是 SQLite，同一套表
应用数据  iCogtiveFlow.db         ← 软件自身数据（最近工程、语言等）

两张表的建表语句（一个字都没多）：

CREATE TABLE objects( id int(32) primary key, type text not null, tags text, data blob);
CREATE TABLE singles( id text primary key, data blob);
表用途实测内容
objects一切"多个"的东西 国轩工程 1247 行 = UniverseImageInfo×1247 + Node×2 + Connection×1
singles一切"一个"的东西（工程级单例） $NextId / $name / $identifier / $version / $createTime / $lastOpenPath / $lastOpenTime； $ 前缀 = 保留键约定

data 是 blob，序列化格式为 Qt QDataStream（字符串是 UTF-16LE + 4 字节长度前缀）。 这是私有格式 —— 不建议照抄，但"objects + singles 兜住一切"这个极简思路值得学。

3.2 三类核心对象的字段（解码结果）

Node节点

NodeId · NodeType · Name · SaveName
NodePosX · NodePosY · Root · Url · Version
Params{…} · Data{…} · Tags · Permission
TrainModelId · InferModelId
InferModelType · InferSetType · NewestModel
CreateTime · IsNewNode

实测 NodeType 取值：DiskImage / Segmentation2D / NewNode（未配置）。
关键设计：节点同时持有训练模型和推理模型的引用，且可指向不同模型 —— 训一个、上另一个。

Connection连线

ConnType · Id
TailNodeId · TailPortIdx · TailPos
TipNodeId · TipPortIdx · TipPos

边是带端口索引的有向连接（Tail=源，Tip=目标），外加两个端点的画布坐标（为了重开时折线还原）。
我们的 flow/ 目前是 (from_node, to_node) 级别 —— 缺端口这一层。多输入/多输出节点必须补上。

UniverseImageInfo全局图像池（这个名字我特别喜欢）

Uid · SrcImageId · SrcNodeId · SrcPath · Tags · Url · Root
  • Uid 是全局唯一标识，形如 1000100-1a00a-c31c77d1-56b708d2；全工程任何地方引用图片都用 Uid。
  • 图片被"收编"进工程：Url = 节点目录内的托管副本路径（如 DiskImage_…/images/1_106_0114_16_te_0.BMP）， 同时 SrcPath 保留原始外部路径（含来源批次，便于溯源）。
  • 工程自包含 ⇒ 拷走工程目录就能复现；来源可溯 ⇒ 能回答"这张图哪来的"。

对照我们：DL Studio 的图片是"项目 images/ 目录扫描 + 名字做键"。 一张图改名/换批次就会断链。引入 Uid + 托管副本 + 源路径三件套，能同时解决 换批次数据对齐（你常做的 te_0/1/2 配对）和溯源。

它的模型版本策略（三个细节，都可以直接学）

现象含义
SG_Tiny_V1 … V13 每次训练自动新建版本目录，永不覆盖 —— 和你做 PPT 的 v9→v49 习惯同源
SG_Tiny_V1_40_GPU.net 同一模型按目标 GPU 架构预导出一份（40 系）。避免上线时现场重新编译 engine 的等待
SG_Tiny_V5(SG_Tiny_V4.net) 目录名直接写明"本版本复用 V4 的模型"，且该目录没有 loss 文件（因为没重训）——用命名代替元数据文件

每个版本目录里固定三个文件：{名}.net（模型）、loss.csv、loss_val.csv、res.dat（推理结果缓存，15 MB）。
loss.csv 的横轴 不是 epoch 而是归一化到 0→1000 的进度（实测 217,000 行、每 step 一行），所以不同轮数的训练曲线可以直接叠在一起比。 loss_val.csv 只稀疏记了 12 个点（1/41/111/241/251/531/581/681/721/803/815/895）。

3.4 标注格式 v5.3.1（它叫 labelMe，但已经不是 labelme）

{
  "baseData": [ { "Roi": {"h","w","x","y","phi"}, "category": "", "dataSet": "Train" } ],
  "shapes": [ { "description": "Region",     ← 形状的语义类型
                "label": "__ignore__",        ← 忽略区（和我们一致）
                "points": [[x,y], ...],
                "shape_type": "polygon",
                "eraser points": [],          ← 橡皮擦轨迹也会被存下来
                "group_id": null, "flags": {} } ],
  "imagePath", "imageWidth", "imageHeight", "imageSet", "flags", "imageData", "version"
}
设计点说明 / 对比我们
baseData.Roi 带 phi ROI 是"旋转矩形"，独立于画在 shapes 里的缺陷。
我们是"图有一个 ROI + shapes 里画缺陷"混在一层 —— 它的分层更清楚： baseData = 这张图怎么用（ROI / 类别 / 属于哪个集），shapes = 图上画了什么
dataSet 写在标签里 数据集划分不存单独文件，就存在每张图的标签里。
好处：图跟着标签走，不会出现"改过名之后 split.json 对不上"。我们用的是单独 train_test_split.json，改图名会断链
shapes[].description 形状有语义角色（实测 "Region"，推测还有缺陷/擦除等）。我们只有 label
__ignore__ 和我们一致 —— 说明我们这条已经对齐了行业惯例，不用改

三个设计要点（都可直接借用）

  1. 模态门控：说明书原文 —— "图像工具节点决定了可用的 Ai 工具类型…若图像与 Ai 工具不对应，无法进行配置"。
    即：连线阶段就禁止非法组合，而不是等到训练时报错。
    → 我们的 flow/ 应该给每个节点声明「输入 modality」和「输出 modality」，连线时校验。
  2. 工具集命名与 nets 命名严格对应：cl=分类 / sg=分割 / od=检测 / rod=旋转检测 / isg=实例分割 / kpd=关键点 / ocl… / ad=异常 / ed=边缘 / mcl/msg=多图 / *3d/*mixed。 _tiny/_small/_medium/_large 四级容量阶梯（实测 tiny 5.7 MB → large 49.8 MB）。
  3. 对比分割/对比分类（CP）：导入时组大小设为 2，一组是"标准图"、一组是"检测图"， 按序号一一对应，模型学的是"差异"。
    → 这正好对上你的一个真实痛点：来料差异导致 OK 图本身长相不同（187 料 vs 233 料）。用"标准图 vs 检测图"的差分式建模，可以从原理上绕开"来料变了模型就过杀"。

3D 单图 tif/tiff 32 位浮点高度图；"产品高度存在差异但灰度差异不大时" 我们目前把形状图当 2D 8 位图用 —— 丢了高度信息。若要提升凹凸点判别，保留 32 位浮点做真 3D 是方向
2D+3D 1 张高度图 + 1 张灰度图，合并成一个张量作为模型输入；工具 = 混合分割/混合分类 我们已有"混合分类"（ui/mixed_viewer.py / mixed_add_dialog.py），思路一致

多图模式的三个交互细节： ① 图像操作界面变成分组显示窗口（单张/多张切换、组内上一张/下一张、窗口排列方式）； ② "组内操作绑定"——在一张图上做 ROI/掩膜/标注，会同步复制到组内其他图； ③ 定位是"将一组图像融合为一张图像处理"，即模型输入是多通道张量，而非多个独立模型。
→ 对我们的启示：三图数据的标注成本是 3 倍，靠"组内绑定"能压回 1 倍。这条性价比极高。

训练 PatchSize / StepSize / ReceptiveField / ByPatch / Capacity 这是最大的空白。大图（相机 1160×460 甚至 1640×4200）不可能整图送网络， 必须滑窗。PatchSize=窗口大小、StepSize=步长（有重叠就融合）、 ReceptiveField=特征尺寸。
说明书给的工程规则："较大缺陷设较大块，较小缺陷设较小块；小图优先整幅训练，效果优于分块"； 还有"分块太大易显存不足"
增广 10 种 × (阈值 + Switch) 我们缺"每个增广独立开关"，缺悬停预览（把鼠标放在参数上就能看到增强后的效果图）
后处理 Score / Area / Gray / Contrast / AspectRatio / Width / Height / Angle + MaxDetectCount 我们完全没有这一层。它的说明书明确写："推理参数用于过滤模型推理后的检测结果， 并判断模型文件的性能效果" —— 也就是说， 评估指标是在应用了后处理过滤之后算的。这和你上次讨论分割评估时的口径问题是同一件事
可视化 VCategory / VRadius / VCenterRegionRadius / VPredictSortOrder 用 V 前缀把"显示相关"参数和"业务相关"参数物理隔离。 好处：客户现场调显示不会碰到业务参数。这个约定很便宜，建议直接采用

两条可以把整份参数表变得可控的范式

  1. {参数} + {参数}Switch 成对：启用与否、阈值多少是两个维度。 我们现在的增强是"一个总开关 + 三个写死的强度"，改强度会连带改变行为。
  2. 推理参数可切换"作用于哪个数据集 / 哪个模型"：可以拿同一组后处理参数， 横向对比 V1…V13 的效果，选出最优模型 —— 这是它版本管理闭环的最后一块拼图。

关于"对比分割 / 对比分类（CP）"—— 单独提一条

它有一个我们没有的工具类别：导入两组图（标准图 + 检测图），按序号一一对应，模型学"差异"。

这在你当前项目里的价值可能被低估了：187 料（3/4 号机，来料好）和 233 料（5/6/8 号机，NG 率 60–78%）的 OK 图本身就长得不一样。用普通分割/分类，模型会去学"来料长相"而不是"缺陷"，一换来料就崩。 对比式建模从原理上把"来料差异"减掉，只留下差异区域。
这条要不要做、以及要不要先在某个缺陷上试点，需要你判断——我不猜。
