## 一、问题：一个全局 `_stop_flag` 撑起了六个流程

清单里写的病灶是"`self.trainer` 单槽 + `self._stop_flag` 全局"，实际读下来比这两句更糟：

| # | 现象 | 触发条件 |
|---|---|---|
| 1 | **连坐**：取消排队中的推理，正在跑的训练一起停 | 训练跑着，队列里还有一行推理，点那行的 × |
| 2 | **秒停**：取消过一次之后，后面每个任务在第一步就停 | 任何一次取消，只要某处 `finally` 漏了复位 |
| 3 | **分类训练根本不走队列** | `_start_cls_training` 是裸 `threading.Thread` —— 队列的串行保证管不到它，它和分割训练共用同一个标志；点"开始分类训练"会把正在跑的分割训练的取消状态抹掉（`self._stop_flag = False`） |
| 4 | **提交即抹**：`_start_training` / `_batch_inference._run` 在**提交那一刻**就清全局标志 | 用户刚点的取消被这一下悄悄干掉（任务还没开始跑） |
| 5 | **停止按钮不分类**：`_stop_batch`（推理按钮）与 `_stop_training`（训练按钮）都只是把全局标志置 True | 点"停止推理"停的可能是训练 |

只有第 2 条被上一轮"局部快照 + 只清自己那个"补过 —— 那是治症状。

## 二、改法：标志挂在任务上，全部接线改成问"我这个任务"

### 1. `ui/task_queue.py`

```python
@dataclass
class Task:
    cancel_requested: bool = False      # 唯一的那份状态
    phase: str = ""                     # ""|preparing|training|validating|saving|inferring

    @property
    def stop_flag(self):  return bool(self.cancel_requested)
    @stop_flag.setter
    def stop_flag(self, v): self.cancel_requested = bool(v)
```

- **刻意不新增字段**：`stop_flag` 只是 `cancel_requested` 的别名。两份状态迟早打架，
  而"哪个才算数"这种问题在并发路径上最难查。
- `_Ctx.phase(name)` 上报阶段（只给 UI 显示，不参与判断）；
  `_Ctx.stop_requested` 给 `stop_check=` 用。
- 新增 `TaskQueue.running`：「停止」按钮靠它找目标（原来 `_running` 是私有的）。

### 2. `ui/main_window.py`

| 位置 | 改法 |
|---|---|
| 分割训练 `_start_training` | `stop_check` 用 `_qctx.task.stop_flag`；**提交时不再清全局**；`finally` 里只有老路径（无队列）才复位 |
| 分类训练 `_start_cls_training` | **登记成 TRAIN 队列任务**，训练器在任务线程里构造（每任务一份）；标志同样用自己的 |
| `_on_task_cancel` | 删掉 `self._stop_flag = True`（连坐的直接来源） |
| 新增 `_cancel_running_task(kind)` | 「停止」按钮只打**同类**正在跑的那个 |
| 新增 `_active_stop()` | 深层循环（`BatchRunner` / OCR）拿不到 ctx，统一从这里问：有任务上下文就问任务，没有才看全局 |
| 批量推理 5 处 `self._stop_flag = False` | 改成"仅老路径复位"（直接点按钮那条路仍要清） |
| 循环里 4 处 `if self._stop_flag:` | 改成 `if self._active_stop():` |
| `BatchRunner(stop_check=...)` 2 处 + OCR/OCV 2 处 | 改成 `self._active_stop` |

### 3. 为什么 `self.trainer` 槽位**没动**

- 分段训练的第二个 TRAIN 会被 `_start_training` 的守卫直接挡掉（提示语保留），
  队列又保证串行 ⇒ 不存在"两个 trainer 抢一个槽"。
- 分类训练的训练器本来就在任务线程里现建（`self._cls_trainer`），天然一任务一份。
- 真正需要"每任务一份"的是**停止标志**，那才是连坐/秒停的载体 —— 已经改完。
  把 trainer 也搬到任务对象上属于纯重构（P1 的范围），本轮不动。

## 三、验证：构造"A 正在跑、B 在排队"的时序（不是"跑一遍不崩"）

`tests/test_task_isolation.py`，10 条：

| 用例 | 钉住什么 |
|---|---|
| 两个任务标志互不影响 | 取消 B，A 的 `stop_flag` / `ctx.stop_requested` 必须还是 False |
| 取消一个后下一个不秒停 | A 被取消后新提交的 C，第一次检查就必须是"没被要求停" |
| phase 上报 | `ctx.phase("validating")` 落到 `task.phase` |
| `stop_flag` 单一来源 | 写 `stop_flag` 必须同步到 `cancel_requested`（反之亦然） |
| `queue.running` | 有任务时指向它，空闲为 None |
| ★ 取消排队项不动全局标志 | 真 MainWindow：`_on_task_cancel` 不许再动 `self._stop_flag` |
| ★ 停止按钮只打同类任务 | `_stop_batch()` 不许停训练；`_stop_training()` 才停 |
| ★ `_active_stop` 优先看任务标志 | 全局被别的路径置 True 时，有任务上下文仍返回 False |
| ★ 新任务不需要谁复位 | 上一个任务被取消后，下一个的 `stop_flag` 必须是 False |
| ★ 分类训练走队列且标志接对 | 假训练器跑通整条链：提交的是 TRAIN、`stop_check()` 跟着任务标志变、提交时没动全局、训练器在任务线程里构造 |

## 四、请重点核对

1. **停止按钮的语义变了**：「停止推理」现在只取消 INFER 任务，「停止训练」只取消 TRAIN。
   以前两个按钮都作用于同一个全局标志（谁在跑就停谁）。如果现场有人习惯了
   "点任意一个停止按钮都能把当前任务停下"，这里会变成"点了没反应"。
   —— 无队列控件时（老路径）仍然退回全局标志，行为不变。
2. **分类训练现在会排队**：分割训练跑着时点"开始分类训练"，它不再并发启动，
   而是排在后面，状态栏显示 `Queued...`。这是队列本来的设计意图（单卡不能并发），
   但**现场习惯会变**：以前点下去就开始跑（然后 OOM/抢显存），现在要等。
3. **`self.trainer` 槽位保留**：理由见第二节第 3 点。如果后续要做 P1-8（业务控制器拆分），
   可以顺手把 trainer 也挂到任务对象上。
4. **检测训练（YOLO）仍走全局标志**：它本来就不进队列（`_start_det_training` 裸线程、
   有自己的 `_det_trainer.stop()`），本轮只把它的"顺手清全局"改成了"仅老路径"。
   要彻底统一得先让它入队，属于下一轮。
