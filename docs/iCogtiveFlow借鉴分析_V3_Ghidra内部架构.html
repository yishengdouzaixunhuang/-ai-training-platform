为什么会卡在 REA 的 Windows 原生插件上

REA 的 Ghidra 通道在 Windows 上依赖一个自带的原生插件 rea-windows-x64.node（848 KB）。它加载成功，但自检 inspect 会抛：

Delete owned object by handle failed
  [C:\Users\ADLINK\AppData\Local\Temp\rea-native-probe-...] (Win32 5): 拒绝访问。

我逐项做了排除实验，下面每一条都有实测，不是推测：

怀疑点实测结果结论
本机 safe-delete 钩子拦截删除Python 直接 os.remove 与 SetFileInformationByHandle 按句柄删除，在 %TEMP%、E:\ 下全部成功（err=0）排除
权限不足残留的 rea-native-probe-* 目录 icacls 显示当前用户 (OI)(CI)(F) 完全控制 + SYSTEM(F)排除
文件系统不匹配C / D / E 全部为 NTFS排除
路径含重解析点%TEMP% 全路径 GetFileAttributesW 无 FILE_ATTRIBUTE_REPARSE_POINT排除
job object 限制带 CREATE_BREAKAWAY_FROM_JOB 脱离 job 后同样失败排除
TEMP 位置特殊把 TEMP 改到 E:\rea_temp（普通目录）后同样失败排除
Node 版本问题Node 22.22.2 与 24.1.0 结果完全相同排除
目录被占用删不掉残留目录为空，外部 rd /s /q 能删掉排除
结论：失败点只在「用它自己持有的句柄删除它自己刚创建的对象」这一步，而创建 / 私有 DACL / 读回校验都已通过。 这是该实验性 P0 通道在特定机器上的自检缺陷，不是配置问题。

并且它是硬依赖：我做过一次对照实验——把 WindowsAuthority.js 里的该检查放行后， doctor 立刻变成 9/9 全绿、provider available=True； 但真跑分析仍然失败，报 Ghidra runtime root creation failed，根因还是同一条 native 错误。 ⇒ native controls 是创建私有 runtime root 的硬依赖，绕过检查只会掩盖问题。 该次实验性改动已完整还原，现在 doctor 如实报告 native 不可用。
所以路线是：REA 的价值在于它的调度与证据链封装，但它的 Windows PE 通路在本机受原生插件所限； 而 Ghidra 引擎本身完全可用。直接用官方 analyzeHeadless， 一样能拿到「函数级 + 类结构级」的证据——本报告的全部内容都来自这条路。

四、六个值得直接照思路做的设计

1. 五态标记：Train / Overkill / Escape / Normal / Doubt

字符串表里连续出现这五个词，同时 UI 控件名里有 btnNormal、btnOverkill、btnEscape、btnMarkClear， 以及 maskCheck / labelCheck / detectCheck 三个图层开关。强证据

这比我在 V2 里建议的「四态」更完整：
Normal（正常）· Overkill（过杀）· Escape（漏检）· Doubt（存疑）· Train（投入训练）
关键在于 Overkill 与 Escape 是并列的一等公民——它把「过杀」和「漏检」做成了同级的现场反馈入口， 而这恰好命中你现场最痛的两件事。存疑（Doubt）单列，避免逼标注员在信息不足时二选一。

2. 难例闭环：推理统计 → 一键转标注

InferStats / InferMsecs / DetectCount      →  每个节点记录推理耗时与检出数
Times:0ms / Avg:0ms / Labeled:0 / Detected:0
"In Conversion..." / "Convert Label" / "Mask To Label"
"Successfully converted the selected detection results into annotations"
"Recrop images"                            →  重新裁剪

这构成一条完整闭环：跑推理 → 看统计 → 挑出可疑结果 → 一键转成标注 → 复查修正。 而且它把「模型检出」与「人工标注」在数据结构上打通了（Mask To Label 说明掩膜与标签可互转）。

3. 标注图形是一等数据模型，不是画布上的像素

CHhGraphData 的 171 个方法几乎覆盖了一个图形对象需要的全部能力：

能力方法证据
三种包围框BoundingRect()→QRectF、BoundingRectangle()→HHRect2I、BoundingRectangle2()→HHRotBox2D
几何推导GenCenterAndAngle(HHPoint2D, double*, double*)（从形状直接算中心与角度）
附着区域GetAttachRegion()→QVector<IAL::HHRegion>
坐标系GetCoordinateType() / GetCurrentCoordinate()→HHCoordinateSys2D
命中检测GetHitDistance() / GetHitID() / GetHitValid() / DoubleHit() / DoubleHitTest()
显示变换GetDisplayScale() / GetDisplayXOffset() / GetDisplayYOffset() / GetDisplayOrder()
绘制样式GetColor / GetFill / GetMask / GetAlpha / GetAnchor / GetEraserRegion
交互状态DrawEnd() / AdjustEnd() / AdjustGraph(QPoint*) / FullsizeGraph(int*,int*)

对照我们的现状：DL Studio 的标注图形更接近「画在画布上的条目」。 把图形提升成带「坐标系 + 命中检测 + 显示变换 + 擦除区」的独立数据模型， 是支撑「缩放/旋转画布后仍能正确编辑」「擦除与反转」「掩膜与标签互转」的地基。

4. 参数与 UI 的绑定被抽象成框架，而不是散落的 setter

LabelPattern / MaskPattern:
    bindFilter(int, IEditControl*, Type)      ← 参数与控件绑定
    codeType(int) → ControlCodeType           ← 每个控件有编码类型
    installEditorGroup(EditorGroup*)          ← 编辑器组安装/卸载
    modes() → EditPatternModeGroup*           ← 模式组
    setControlGroup(unique_ptr<EditControlGroup>)
    onTriggered(int, QVariant*) / onValueChanged(int, QVariant*)

适配器：BoolButtonAdaptor / EnableButtonAdaptor
过滤器：EditControlBindFilter
它把「标注参数」抽象成 Pattern（模式）：一个模式声明自己有哪些参数、 每个参数绑到哪个控件、控件是什么编码类型；再通过 EditorGroup 一次性装/卸一整套控件。 加一个新标注工具 = 加一个 Pattern，而不用改 UI 框架。

我们的对应痛点很实际：三个标注模块（矩形/多边形/画笔）的参数面板各写一套， 加参数就要动 UI 代码。这套模式 + 适配器 + 绑定过滤器的组合值得借鉴。

5. 任务用统一的消息协议，且带「下一步提示」状态机

CHhTask:        onGet(QByteArray*) / onPut(QByteArray*) / handleMessage(QString, QByteArray)
CHhTaskControl: get / put / start / stop (QByteArray) / onTaskFinish(QByteArray)
TaskBase:       checkState() → NextStepHint
                success() / error() / finishCode()
AsyncTempTask / FuncInvoker

三个细节值得抄：① 任务与控制端之间用序列化消息（QByteArray）通信，天然支持跨进程； ② NextStepHint 把「任务当前该做什么」显式建模，而不是让 UI 去猜进度； ③ finishCode() 让失败有可编程的归因，而不是只弹一个字符串。

6. 流程节点模型：节点、端口、类型分开建模

ToolNodeData: id() / name() / pos() / loadData() / saveData(PolicyInNotFound)
ToolPortData: portName() / portType() / dataType() / node() → IFlowNodeData*

端口显式带数据类型（dataType()）与端口类型（portType()）。 这是流程编辑器能做「类型校验、连线合法性、自动补转换节点」的前提—— 也正好支撑 V2 里提到的「工具链接：分割结果当下游 ROI」。

五、映射到 DL Studio：优先级建议

优先级借鉴点为什么先做涉及模块
P0 五态标记（含 Overkill / Escape 平级） 直接吃现场两大痛点（过杀、漏检），且是数据回流的前提；改动集中在数据模型与一列按钮 annotation / 数据集管理
P0 推理统计收口（InferStats / InferMsecs / DetectCount） 当前指标散在评估脚本；收口后才能谈「按节点看效果」 detection / 评估页
P0 难例闭环（检出结果 → 一键转标注 / Mask To Label） 把「发现漏检过杀」到「补进训练集」的链路缩短，是最省人力的那一环 annotation / detection
P1 标注图形数据模型（坐标系 / 命中检测 / 擦除区 / 显示变换） 是「画布缩放旋转后仍可编辑」「掩膜反转」的地基；越晚改成本越高 annotation 核心
P1 参数—控件绑定框架（Pattern + Adaptor + BindFilter） 解决「每加一个参数就改 UI」；但要先有稳定的参数描述，故放 P1 UI 框架
P2 任务消息协议 + NextStepHint + finishCode 收益在中长期（可跨进程、可归因），当前单机场景紧迫度低 任务调度
P2 端口显式数据类型 等做多工具串联时再上 流程编辑器

六、不该照抄的部分

  • 代码一行都不要抄。本报告全部来自静态观测的类名 / 方法名 / 字符串，属于「设计思路」层面的借鉴。
  • Qt 的信号槽元数据机制别硬学。它的 qt_metacall / metaObject 是 Qt moc 的产物，我们的 PyQt5 有现成机制，重复造反而更差。
  • 它的 DACL / Job Object / 重解析点防护不要照搬。那是为一个带加密狗、要在客户现场多机部署的商业产品准备的； 我们是开发工具，套上只会增加排障成本（这轮 REA 的教训就是活例子）。
  • CodeMeter / 深思数盾双加密狗那套不要靠近。合规红线，且与我们无关。
